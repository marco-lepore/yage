Research checked on 20 October 2026. The hotbar owns slot assignments and selection. The game owns the actions, inventory quantities and ability cooldowns.

The sources differ in what a slot means. Opsive documents references, inventory mirrors and collection-owned items as separate choices. This addon implements references. Moving a binding never moves an item or restarts an ability. More Mountains was checked through published documentation and generated API declarations; its proprietary implementation was not available. Swift's public source and consumer scene were inspected directly.

## Decisions

- `Hotbar<TId>` accepts a plain-object binding catalog. TypeScript infers the allowed IDs from its keys. Each binding supplies a label, optional icon key, a live `read()` and a synchronous `activate()` result. Closures adapt abilities, inventory or game components without addon dependencies.
- Availability and activation return a reason when rejected. Cooldowns and counts are read from their owner. Positive cooldowns block activation; counts are display data, since a count of zero does not always mean an action is unavailable. Activation rechecks state and lets the owner reject a race.
- Fixed numbered slots support assignment, clearing, swapping, selection and cyclic navigation. Duplicate bindings are allowed and read the same authoritative owner. Empty/depleted slots remain assigned until explicitly cleared.
- Snapshots contain binding IDs and selection only. Restore validates the entire document before changing state. Owners restore their own item/ability state separately. Unknown IDs fail explicitly.
- `HotbarController` owns the component integration, callback attribution, entity events, input focus and presentation lifecycle. One model has one mounted controller. Inspector reads a plain diagnostic getter; activation and assignment events use the existing entity event stream.
- The default presenter uses renderer components, canvas text, icon keys and a cooldown bar. A flat theme changes dimensions/colors; a presenter interface replaces the whole view. No shared inventory registry or UI grid abstraction is introduced.
- Default controls use YAGE action maps for numbered activation, previous/next, selected activation and clearing. Mouse/touch taps activate; dragging between slots swaps assignments. Custom bindings replace these controls; `input: null` leaves control to the host.
- Ability timelines, held-action release, inventory effects and networking remain with the game. Activation is a synchronous request result, not proof that a long-running ability completed. The runnable example demonstrates `Abilities.send()` and inventory consumption through the same contract.

## Current-tree checks

Abilities is already shipped in this tree. The historical `play()` proposal is stale: the current API is `send()`, `canSend()`, `cooldownRemaining()` and `cooldownRatio()`. Input already owns action maps, pointer claims and pointer generations. Renderer `ensureLayer`, component enable/disable hooks, ErrorBoundary and Inspector reflection provide the required integration mechanisms.
