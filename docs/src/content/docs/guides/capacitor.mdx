---
title: "Mobile with Capacitor"
description: "Ship a YAGE game as a mobile app: app lifecycle, orientation lock, the Back button, and file saves"
---

`@yagejs/host-capacitor` runs a YAGE game as a mobile app. The app's state
reaches the engine, the game locks the screen orientation, the Android Back
button is a key the game binds, and saves are files in the app's private
directory rather than web-view storage the system may reclaim.

A mobile build has two halves. The **app** is the Capacitor app around the
game: its generated iOS or Android project and its `capacitor.config.json`.
The **page** is the game's web page inside the app's web view. This package
runs in the page and talks to the app through Capacitor's official plugins.

## Install

```sh
npm install @yagejs/host-capacitor
npm install @capacitor/core @capacitor/app @capacitor/filesystem @capacitor/screen-orientation
```

The four `@capacitor/*` packages go in the game's own `dependencies`.
`npx cap sync` installs the native half of the plugins the app itself names,
so a plugin that arrives only as another package's dependency reaches the
page with nothing behind it. The game stops at start with a message naming
the package to add.

## The game's entry file

Write one boot function for every target, and one entry file per target that
hands it the plugins that target needs.

```ts yage-group="targets" yage-file="boot.ts"
import { Engine } from "@yagejs/core";
import type { Plugin } from "@yagejs/core";
import { RendererPlugin } from "@yagejs/renderer";
import { SavePlugin, createSave } from "@yagejs/save";
import type { SaveAdapter } from "@yagejs/save";

export interface BootOptions {
  hostPlugins: readonly Plugin[];
  saveAdapter: SaveAdapter;
}

export async function boot(options: BootOptions): Promise<Engine> {
  const engine = new Engine();
  for (const plugin of options.hostPlugins) engine.use(plugin);
  engine.use(new RendererPlugin({ width: 640, height: 360 }));
  engine.use(
    new SavePlugin({ save: createSave({ adapter: options.saveAdapter }) }),
  );
  await engine.start();
  return engine;
}
```

The Capacitor entry installs the plugin and the save adapter without asking
whether it is inside an app:

```ts yage-group="targets" yage-file="main.capacitor.ts"
import {
  CapacitorHostPlugin,
  capacitorSaveAdapter,
} from "@yagejs/host-capacitor";
import { boot } from "./boot.js";

await boot({
  hostPlugins: [new CapacitorHostPlugin()],
  saveAdapter: capacitorSaveAdapter({ profile: "release" }),
});
```

The browser entry installs neither:

```ts yage-group="targets" yage-file="main.web.ts"
import { localStorageAdapter } from "@yagejs/save";
import { boot } from "./boot.js";

await boot({
  hostPlugins: [],
  saveAdapter: localStorageAdapter({ namespace: "my-game" }),
});
```

Each build then carries only what its target needs, and a mobile build that
somehow opens in a browser says so rather than running with the wrong saves.

### One bundle for every target

A game that ships a single bundle asks first. `isCapacitorHost()` comes from
an entry that imports nothing, so a browser build can call it before it loads
the rest of the package:

```ts yage-group="single-bundle"
import { isCapacitorHost } from "@yagejs/host-capacitor/detect";
import { localStorageAdapter } from "@yagejs/save";
import type { Plugin } from "@yagejs/core";
import type { SaveAdapter } from "@yagejs/save";

let hostPlugins: readonly Plugin[] = [];
let saveAdapter: SaveAdapter = localStorageAdapter({ namespace: "my-game" });
if (isCapacitorHost()) {
  const host = await import("@yagejs/host-capacitor");
  hostPlugins = [new host.CapacitorHostPlugin()];
  saveAdapter = host.capacitorSaveAdapter({ profile: "release" });
}
```

The drawback: a page outside an app takes the browser branch in silence, so a
build meant for a phone runs as a browser game and writes its saves to the
browser's storage.

## Generating the native projects

The Capacitor CLI builds the projects around the built web directory:

```sh
npx cap add ios --packagemanager SPM
npx cap add android
npx cap sync
```

Every plugin this package uses ships a `Package.swift`, so an iOS project
needs no other dependency manager. Two settings in `capacitor.config.json`
belong to this package:

- `ios.contentInset` is `"never"`, so the web view goes edge to edge and the
  page's own CSS pads for the safe areas.
- `App.disableBackButtonHandler` stays unset, so Back reaches the game.

## What the game gets

The iOS behaviour in this section was checked on the iOS simulator: switching
to another app and back, one orientation lock, the save files, and stopping
the app during a stream of saves. A call, Control Centre, a system alert or a
permission dialog on an iPhone, and every Android behaviour on this page,
follow from Capacitor's source code and have not been run.

### Who is running it

`engine.host.info` reports `{ runtime: "capacitor", os, appVersion,
appBuild }`. `os` is `"ios"` or `"android"`; the version and the build number
come from the native project.

Use them for a diagnostics screen, never to decide what the game offers.
`renderer.fullscreenSupport`, `renderer.orientationLockSupport` and the other
support values say what this host can do.

### App state

`engine.host.active` turns `false` when the player takes a call, pulls down
Control Centre, answers a permission dialog or leaves for another app, and
`true` again on the return. Scenes with `scenes.autoPause` and audio with
`audio.autoPause` follow it, so a game needs no code of its own for the trip.

What the app reports on each system:

| Field        | iOS                                                      | Android                                                |
| ------------ | -------------------------------------------------------- | ------------------------------------------------------ |
| `activity`   | the app losing and regaining interaction                 | the activity pausing and resuming                      |
| `visibility` | the window leaving and coming back                       | the activity being stopped and started                 |
| `focus`      | the page's own                                           | the page's own                                         |

### Orientation and fullscreen

`renderer.lockOrientation("landscape")` asks the app for the lock and
resolves with the orientation the page reads once the screen has turned. A
lock the system does not perform — an orientation the iOS project does not
list, or a large Android screen on Android 16 with target SDK 36 — settles
after two seconds with the screen as it was, so compare the result with what
you asked for:

```ts yage-group="lock"
import type { RendererPlugin } from "@yagejs/renderer";

export async function goLandscape(renderer: RendererPlugin): Promise<boolean> {
  if (renderer.orientationLockSupport !== "supported") return false;
  const turned = await renderer.lockOrientation("landscape");
  return turned?.startsWith("landscape") ?? false;
}
```

`renderer.fullscreenSupport` is `"unsupported"` in an Android web view: it
leaves fullscreen in the same call that enters it, so a button would do
nothing. On iOS the web view answers for itself. Read the support value
before offering the button.

### The Android Back button

A press arrives as the key `"BrowserBack"`, so a game binds it in its action
map like any other key:

```ts yage-group="back"
import { InputPlugin } from "@yagejs/input";

const input = new InputPlugin({
  actions: { back: ["Escape", "BrowserBack"] },
});
```

With no action bound to the key, a press moves the app to the background and
leaves the game where it was, which is what Android itself does at the root
of an app. That is also what a key held by a disabled action group gives: the
press is delivered and nothing happens. On a screen where Back should leave
the app, unbind the key there:

```ts yage-group="back"
import type { InputManager } from "@yagejs/input";

export function letBackLeaveTheApp(manager: InputManager): void {
  manager.unbindKey("back", "BrowserBack");
}
```

### Saves

`capacitorSaveAdapter({ profile })` writes each key as a file under
`Library/yage-saves/<profile>` in the app's private directory. iOS includes
it in its backup and the Files app does not show it. The directory follows
the app's bundle identifier, so renaming the app leaves the saves where they
are, and a test build and a release build never read each other's slots.

A write that resolved is held when the system kills the app in the
background. Neither system's write reaches the storage hardware, so a power
loss is not guaranteed; a game that cares takes its checkpoints at moments
the player can repeat.

## Errors you may see

- `CapacitorHostPlugin.install: this page is not running inside a Capacitor app. Leave this plugin out of a browser build.` — the mobile entry's bundle opened in a browser.
- `CapacitorHostPlugin.install: the @capacitor/app plugin is not in this app. Add "@capacitor/app" to the app's package.json dependencies and run npx cap sync.` — the plugin's native half is missing. The same message names the other packages.
- `capacitorSaveAdapter: profile must match ^[a-z][a-z0-9-]*$, got "Release".` — the profile names the save directory, so it is lower case.

If Xcode stops at a GitHub credential prompt while it resolves a Swift
package, add `-packageAuthorizationProvider netrc` to the `xcodebuild` call.
