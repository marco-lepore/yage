YAGE uses PixiJS v8 under the hood for all rendering. The `@yagejs/renderer`
package provides components and systems that keep PixiJS in sync with the ECS
world automatically — you work with components and the display system handles
the rest.

## RendererPlugin Setup

Register the renderer when creating your engine:

```typescript yage-context="engine"
import { RendererPlugin } from "@yagejs/renderer";

engine.use(
  new RendererPlugin({
    width: 1280,
    height: 720,
    backgroundColor: 0x1a1a2e,
    container: document.getElementById("game")!,
  }),
);
```

The plugin creates the PixiJS application, sets up the render loop, and
registers all rendering systems.

### Pixel-art preset

If you're shipping pixel art, set `pixelArtPreset: true`. One flag flips
the three settings that otherwise need to be tracked down individually:

- `TextureStyle.defaultOptions.scaleMode = "nearest"` — freshly loaded
  textures sample without bilinear blur.
- `roundPixels: true` on the Pixi `Application` — subpixel transforms
  don't smear sprite edges.
- `image-rendering: pixelated` (with a `-webkit-optimize-contrast`
  Safari fallback) on the canvas element — the browser scales the
  backing store with nearest-neighbor instead of bicubic.

```typescript yage-context="engine"
import { RendererPlugin } from "@yagejs/renderer";

declare const host: HTMLElement; // the page element that holds the game

engine.use(
  new RendererPlugin({
    width: 320,
    height: 240,
    container: host,
    pixelArtPreset: true,
  }),
);
```

The preset composes with `pixi: {...}` — explicit options win, so
`pixi: { roundPixels: false }` overrides the preset's default. Per-texture
overrides (`source.scaleMode = "linear"`) keep working too — the preset
only changes the *default* sampling mode.

### Which graphics API runs

Pixi tries WebGL, then WebGPU, then a plain 2D canvas, and draws with the
first one the browser supports. `pixi: { preference: "webgpu" }` moves WebGPU
to the front of that order. `renderer.backend` reports the one it picked,
`"webgl"`, `"webgpu"` or `"canvas"`, for a game that adjusts its effects to it
or a test that checks it.

## How the components relate to PixiJS

Each visual component draws with one PixiJS display object. Change a visual
through its component and its entity's `Transform`, never through that Pixi
object:

- **The engine owns the Pixi object's state.** `DisplaySystem` writes its
  position, rotation and scale from the entity's `Transform` every frame. The
  component writes its own `visible` and `alpha` onto it whenever either
  changes, when the entity activates, and when a modifier changes. A value
  written on the Pixi object directly is lost at the next of those.
- **A task that needs the Pixi object is a missing component API.** Open an
  issue for it rather than writing to the object.
- **Options forward to PixiJS.** `TextComponent`'s `style` is a pixi
  `TextStyleOptions`, and `GradientFill` is pixi's `FillGradient`. When in
  doubt about an option, the upstream pixi docs are the source of truth.
- **Type aliases, not raw pixi types.** Every exported field, parameter, and
  return type (`VisualComponent.renderObject`, `RenderLayer.container`, ...)
  is typed through `@yagejs/renderer`'s own alias names (`DisplaySprite`,
  `DisplayContainer`, `DrawContext`, `ColorValue`, ...), so your code
  never imports `pixi.js` to name a type. `DisplaySprite` is pixi's `Sprite`
  under another name; the alias changes only the import.
- **An inactive entity draws nothing.** `DisplaySystem` skips it and its
  visuals stay hidden. A tool that shows inactive entities anyway, such as a
  level editor's preview, calls `visual.drawInactive(shown)` once per frame:
  it places the visual at its `Transform` pose and shows it when `shown` is
  `true` and the visual's own `enabled` and `visible` allow it.
