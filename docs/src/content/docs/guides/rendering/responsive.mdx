description: "Fit modes, drawing into bars, HUD anchoring, DOM overlays, fullscreen, and mobile pages"
---

The canvas is **responsive by default**. `RendererPlugin` tracks a host
element and re-maps the virtual rectangle on every resize — no extra config
needed. To pin the canvas at a fixed size, give the container fixed CSS
dimensions; the canvas will track that constant size.

```typescript
import { RendererPlugin } from "@yagejs/renderer";

new RendererPlugin({
  width: 800,
  height: 600,
  container: document.getElementById("game")!,
  // fit: { mode: "letterbox" }  — this is the default
});
```

Pass `fit` to override the mode or the observed element:

```typescript
import { RendererPlugin } from "@yagejs/renderer";

const hostElement = document.getElementById("game")!;

new RendererPlugin({
  width: 800, height: 600,
  container: hostElement,
  fit: { mode: "cover" },                    // change mode
  // fit: { mode: "letterbox", target: other } // observe a different element
});
```

Four modes cover the usual web-game needs:

- **`letterbox`** *(default)* — preserves the virtual aspect ratio and
  centers it inside the host element. Leftover space around the game is painted
  with `backgroundColor` (the "bars"). This is what most games want: no
  distortion, no cropping.
- **`expand`** — same scaling as `letterbox` (virtual is always fully
  visible), but the game draws into the bars instead of leaving them blank.
  Pair with `extendedVirtualRects` to render fog, parallax, or a decorative
  backdrop into the play-adjacent space. Matches Godot's `expand`, Unity's
  `Expand` match mode, and Construct 3's "Scale inner."
- **`cover`** — preserves aspect and fills the host element edge-to-edge,
  CSS-cover style. Whichever axis has the wider aspect ratio gets overflow
  clipped by the canvas boundary. Rarely the right choice for gameplay —
  aspect ratio changes what the player can see. Good for full-bleed
  backgrounds or splash screens.
- **`stretch`** — scales each axis independently to fill the host element. Distorts
  the image; use sparingly (menus, editor panels, deliberate stylistic
  effects).

`letterbox` and `expand` apply the exact same stage transform. The
difference is a rendering convention: under `letterbox` the bars are the
flat background color, under `expand` the game is expected to fill them.

`fit.target` defaults to the `container` you passed, or the canvas'
`parentElement`. There is no `document.body` fallback — a `ResizeObserver`
on `body` fires on any page layout change, not just viewport resizes. With
no host element to observe, the fit applies once against the configured
`width × height`. Pass `fit: { target: document.body }` to opt in, or name
any other element. `setFit({ mode })` changes the mode and keeps the target
already in use.

A `ResizeObserver` drives the updates, and stage scale and position are
recomputed to map the virtual rectangle into the new canvas per the active
mode. In headless environments (no DOM target) the plugin applies a one-shot
transform against the initial `width × height` and installs no observer.

The canvas backing store follows the display's pixel ratio, so the game stays
crisp on a HiDPI screen, after a window moves to a display with another ratio,
and after a browser zoom. Set `resolution` in the renderer config to fix the
density instead: that value is then kept whatever the display does, which caps
the texel count on a very dense screen.

:::caution[Give the fit container a bounded height]
The host element's measured size is fed back into the canvas on every resize, so a
container that has **no height of its own** — one whose height is driven
purely by its content — has no stable size, and the observer can grow it
without bound. Browsers default `<canvas>` to `display:inline`, which adds
a ~4px baseline gap below it that makes this loop kick in even with no
other CSS. The renderer defends against this automatically by setting
`display:block` on its canvas, so the common case converges with zero
effort — but you should still give the fit container an explicit or bounded
height: `height: 100%` under a sized ancestor, a fixed pixel height, or a
`max-height`. If a genuine feedback loop is detected despite the
`display:block` reset (e.g. a stray vertical margin on the canvas or
sub-pixel rounding), `FitController` freezes auto-resize at the last good
size and logs a one-time `console.warn` explaining the fix, rather than
letting the page grow until it hangs.
:::

At runtime you can switch modes or observe a different element:

```typescript yage-context="scene-enter"
import { RendererKey } from "@yagejs/renderer";

const renderer = this.use(RendererKey);
const [cssX, cssY] = [120, 80]; // a point on the canvas, in CSS px
const [x, y] = [400, 300]; // a point in virtual space

renderer.setFit({ mode: "expand" });     // swap modes / target
renderer.fit;                              // current { mode, target? }
renderer.canvasSize;                       // { width, height } in CSS px
renderer.canvasToVirtual(cssX, cssY);      // invert the stage transform
renderer.virtualToCanvas(x, y);            // forward transform (virtual → CSS px)
renderer.visibleVirtualRect;               // on-screen sub-rect of virtual space
renderer.croppedVirtualRects;              // virtual regions off-screen under cover
renderer.virtualCanvasRect;                // where virtual sits on canvas (CSS px)
renderer.visibleCanvasRect;                // full canvas extent in virtual px
renderer.extendedVirtualRects;             // bars outside virtual (letterbox/expand)
```

## HUD anchoring under `cover`

In `letterbox` / `expand` / `stretch` the full virtual rectangle is always
on-screen, so HUDs anchored to `virtualSize` corners stay visible. Under
`cover` the long axis gets cropped — a HUD anchored to virtual `(0, 0)`
can end up off-screen. `renderer.visibleVirtualRect` returns the
currently-visible sub-rect of virtual space (clamped to virtual bounds),
so HUD code can track what the player actually sees while gameplay keeps
operating in the full declared virtual space:

```typescript yage-context="scene-enter"
import { Transform } from "@yagejs/core";
import { RendererKey } from "@yagejs/renderer";

const renderer = this.use(RendererKey);
const scoreLabel = this.spawn("score").add(new Transform());

// Gameplay: always the full declared play area.
const { width, height } = renderer.virtualSize;

// HUD: follow the visible sub-rect so corner-anchored elements stay on-screen.
const visible = renderer.visibleVirtualRect;
scoreLabel.setPosition(visible.x + 16, visible.y + 16);
```

Under `letterbox` / `expand` / `stretch` `visibleVirtualRect` equals
`{ x: 0, y: 0, width: virtualWidth, height: virtualHeight }` — no change
needed for non-cover games. This distinction matters for competitive
titles where a wider viewport must not let players see more of the play
area than narrower ones do.

## Drawing into the bars under `expand`

Under `expand` the game is expected to render into the extra canvas area
around the virtual rect. Two getters describe that space:

- `renderer.visibleCanvasRect` — full canvas extent in virtual-space
  pixels. Extends past `virtualSize` on the bar axis (negative `x`/`y`,
  dimensions larger than the virtual rect) whenever aspect mismatches.
  Iterate gridlines or backdrops against this rect so they cover every
  on-screen pixel, not just the play area.
- `renderer.extendedVirtualRects` — 0–2 rectangles of the visible canvas
  that sit outside virtual, in virtual-space pixels. Exactly the bars.
  Empty on an aspect-matched host element, under `cover`, and under `stretch`.

```typescript yage-context="scene-enter"
import { Transform } from "@yagejs/core";
import { GraphicsComponent, RendererKey } from "@yagejs/renderer";

const renderer = this.use(RendererKey);
const hud = this.spawn("hud").add(new Transform());

// Backdrop that fills the whole canvas, extending into bars under expand:
const canvas = renderer.visibleCanvasRect;
this.spawn("backdrop").add(new GraphicsComponent()).draw((g) => {
  g.rect(canvas.x, canvas.y, canvas.width, canvas.height)
    .fill({ color: 0x0f172a });
});

// Fog-of-war over the bars:
this.spawn("fog").add(new GraphicsComponent()).draw((g) => {
  for (const bar of renderer.extendedVirtualRects) {
    g.rect(bar.x, bar.y, bar.width, bar.height)
      .fill({ color: 0x000000, alpha: 0.78 });
  }
});

// HUD that follows the canvas corners (so cards live in the bars):
const cornerTL = renderer.visibleCanvasRect;
hud.setPosition(cornerTL.x + 16, cornerTL.y + 16);
```

`extendedVirtualRects` is populated under `letterbox` too, geometrically
identical to `expand`, but under that mode it only reports where the bars
are. `letterbox` clips every world and screen layer to the virtual rect, so
anything drawn at those coordinates on such a layer is invisible.

To put a scoreboard or branding in letterbox bars, declare a layer with
`space: "canvas"`. A canvas layer is drawn in **canvas pixels**, outside the
fit scale and the letterbox clip, so it reaches the bars. It draws above every
scene's other layers and ends with its scene, like any layer.

```typescript
import { Scene, Transform } from "@yagejs/core";
import { GraphicsComponent, RendererKey } from "@yagejs/renderer";
import type { LayerDef } from "@yagejs/renderer";

class BrandedScene extends Scene {
  readonly name = "branded";
  readonly layers: readonly LayerDef[] = [
    { name: "bars", order: 0, space: "canvas" },
  ];

  onEnter(): void {
    const renderer = this.use(RendererKey);
    const { width } = renderer.canvasSize; // CSS px
    const play = renderer.virtualCanvasRect; // play area, in canvas px

    const branding = this.spawn("branding");
    branding.add(new Transform()); // (0, 0) is the canvas's top-left corner
    branding.add(new GraphicsComponent({ layer: "bars" })).draw((g) => {
      g.rect(0, 0, width, play.y).fill({ color: 0x0f172a }); // top bar
    });
  }
}
```

A canvas layer's coordinates do not follow a resize, so redraw its content
from the new `canvasSize` and `virtualCanvasRect` when the canvas changes
size. No camera binds a canvas layer, and a camera whose `bindings` names one
throws when it is added. The scene's own `fx` and `setMask` do not cover it;
the renderer's screen-scope `fx` does. A scene transition draws its overlay
under canvas layers, so `fade`, `flash` and `iris` leave them in view unless
you pass `coverScreen: true`.

## Reasoning about the cropped region under `cover`

`renderer.croppedVirtualRects` returns the complement of
`visibleVirtualRect` inside `virtualSize` — the 0–2 strips of virtual
space that are off-screen. Empty under `letterbox` / `expand` / `stretch`;
under `cover` it's the top+bottom or left+right crop strips.

Use it when an effect needs to know "what's beyond the player's view"
specifically under `cover`: fog-of-war overlays that fade at the crop
boundary, indicators that pulse when off-screen enemies are nearby,
auto-panning cameras.

## Positioning DOM overlays

`renderer.virtualCanvasRect` tells you where the play area lives on the
canvas in **CSS pixels** — useful for absolutely-positioned HTML overlays
(menus, tooltips, inspector panels) that should track the virtual rect
rather than the canvas:

```typescript yage-context="scene-enter"
import { RendererKey } from "@yagejs/renderer";

const renderer = this.use(RendererKey);
const menuEl = document.getElementById("menu")!;

const r = renderer.virtualCanvasRect;
menuEl.style.left = `${r.x}px`;
menuEl.style.top = `${r.y}px`;
menuEl.style.width = `${r.width}px`;
menuEl.style.height = `${r.height}px`;
```

Pair with `virtualToCanvas(x, y)` for single-point DOM mapping.

The built-in `responsive-ui` example demonstrates `expand`: the grid
extends across the whole canvas, fog covers the bars, and HUD cards
anchor to `visibleCanvasRect` corners — landing in the bars whenever
aspect mismatches.

Note on terminology: "screen" elsewhere in the engine (UI `LayerSpace:
"screen"`, `Camera.screenToWorld`) means *virtual viewport space*, not DOM
pixels. The `canvasToVirtual` method is named after its actual inputs (CSS
pixels relative to the canvas top-left) to avoid that collision.

When you use `@yagejs/input` alongside fit, pointer events and
coordinates wire up automatically. `RendererPlugin` registers itself
under `RendererAdapterKey` (from `@yagejs/core`), and `InputPlugin`
resolves that key during install — so pointer events target the canvas
and coordinates route through `canvasToVirtual` with no config. Just
make sure you register `RendererPlugin` before `InputPlugin`.

```typescript yage-context="engine"
import { RendererPlugin } from "@yagejs/renderer";
import { InputPlugin } from "@yagejs/input";

const hostElement = document.getElementById("game")!;

engine.use(
  new RendererPlugin({ width: 800, height: 600, container: hostElement }),
);
engine.use(new InputPlugin({ actions: { /* ... */ } }));
```

## Fullscreen

`RendererPlugin` is the one place a game asks for fullscreen, whichever
application runs it: a browser tab, or a native shell around a web view. On a
page the element that goes fullscreen is the configured `container` when there
is one, so DOM overlays beside the canvas stay inside the area shown
fullscreen, and the canvas itself otherwise.

In the Electron shell of `@yagejs/host-electron`, fullscreen is the window's,
whatever started it: the application menu, the window's own button, or
`requestFullscreen()`. See [Desktop with Electron](/guides/electron/).

In a Capacitor app with `@yagejs/host-capacitor`, fullscreen comes from the
page on iOS and is `"unsupported"` on Android, whose web view leaves
fullscreen in the call that enters it. Reading `fullscreenSupport` before
offering the button covers both. See
[Mobile with Capacitor](/guides/capacitor/).

```typescript yage-context="engine,async"
import { RendererPlugin } from "@yagejs/renderer";

const hostElement = document.getElementById("game")!;
const button = document.getElementById("fullscreen")!;

const renderer = new RendererPlugin({
  width: 800,
  height: 600,
  container: hostElement,
});
engine.use(renderer);
await engine.start();

button.hidden = renderer.fullscreenSupport === "unsupported";
button.addEventListener("click", () => {
  const toggle = renderer.isFullscreen
    ? renderer.exitFullscreen()
    : renderer.requestFullscreen();
  toggle.catch((err: unknown) => console.warn(err));
});
```

| Member | Purpose |
|---|---|
| `requestFullscreen(): Promise<void>` | Present the game fullscreen. Resolves without asking the host when the game is fullscreen already. |
| `exitFullscreen(): Promise<void>` | Leave fullscreen. No-op if not currently fullscreen. |
| `isFullscreen: boolean` | Whether the game is presented fullscreen, read live from the host, so it stays correct when the player exits with Esc, the browser's own control, or a window menu. |
| `fullscreenSupport: HostSupport` | Whether a request can change how the game is presented: `"supported"`, `"unsupported"`, or `"unknown"`. |

The renderer emits `screen:fullscreen` on the engine event bus once per
change, and the event arrives before the promise of a request the game made
resolves. Subscribe through `EventBusKey` to relayout a HUD or update a button
label:

```typescript yage-context="engine"
import { EventBusKey } from "@yagejs/core";

const fullscreenButton = document.getElementById("fullscreen")!;

const bus = engine.context.resolve(EventBusKey);
bus.on("screen:fullscreen", ({ active }) => {
  fullscreenButton.textContent = active ? "Exit fullscreen" : "Enter fullscreen";
});
```

Three rules make a toggle behave the way a player expects:

- A request made while a request is in flight shares that request's promise,
  and one made while an exit is in flight runs after the exit settles. The last
  call wins, so a double click does not fail.
- `requestFullscreen()` rejects where `fullscreenSupport` is `"unsupported"`,
  and with the browser's own error where the browser refuses — on a page it
  must be called from a user-gesture handler (click, touch, key), or the
  promise rejects with a `TypeError`.
- The four members above, and the four orientation members below, are readable
  from the renderer's `onStart` to `engine.destroy()`, because which
  application supplies the state is settled as the engine starts. Outside that
  span each one reports that the display is unavailable, and a plugin that
  reads one in its own `onStart` is registered after `RendererPlugin`.

## Orientation

`renderer.orientation` is the screen orientation, or `null` where the host
cannot read it. Its values are the built-in DOM union: `"portrait-primary"`,
`"portrait-secondary"`, `"landscape-primary"` and `"landscape-secondary"`. The
renderer emits `screen:orientation` on the event bus once per change, with
`{ type: OrientationType }`.

```typescript yage-context="engine"
import { EventBusKey } from "@yagejs/core";

const rotateOverlay = document.getElementById("rotate-device")!;
const showRotateOverlay = () => (rotateOverlay.hidden = false);
const hideRotateOverlay = () => (rotateOverlay.hidden = true);

const bus = engine.context.resolve(EventBusKey);
bus.on("screen:orientation", ({ type }) => {
  if (type.startsWith("portrait")) showRotateOverlay();
  else hideRotateOverlay();
});
```

The event fires only on a change, so read `renderer.orientation` once after
`engine.start()` for the orientation the game starts in.

A game can also ask for one orientation. `lockOrientation(lock)` resolves with
the orientation the host reports once it accepted the lock, which can differ
from what was asked for when the device does not turn — so compare the result
and show a rotate-device overlay when they differ:

```typescript
import type { RendererPlugin } from "@yagejs/renderer";

declare const renderer: RendererPlugin;
declare function showRotateOverlay(): void;

async function askForLandscape(): Promise<void> {
  if (renderer.orientationLockSupport === "unsupported") return;
  const result = await renderer.lockOrientation("landscape").catch(() => null);
  // A lock the host accepted does not guarantee the screen turned.
  if (result === null || result.startsWith("portrait")) showRotateOverlay();
}
```

| Member | Purpose |
|---|---|
| `orientation: OrientationType \| null` | The screen orientation, or `null` where the host cannot read it. |
| `orientationLockSupport: HostSupport` | Whether this host can lock the orientation. `"unknown"` means only an attempt tells. |
| `lockOrientation(lock): Promise<OrientationType \| null>` | Lock the orientation. Rejects where locking is `"unsupported"`, and with the host's error when it refuses. |
| `unlockOrientation(): Promise<void>` | Release a lock. Resolves without action where locking is `"unsupported"`. |

In a Capacitor app with `@yagejs/host-capacitor`, the lock goes through the
app itself: `lockOrientation()` resolves once the screen has turned, or after
2000 ms when the system turns nothing.

`orientationLockSupport` is `"unknown"` in a browser that has the operation:
desktop browsers refuse every lock, and Chrome on Android accepts one only
while the game is fullscreen or installed. Safari has no orientation lock at
all, where the value is `"unsupported"`.

No order is promised between `screen:orientation` and the canvas taking its
new size. Read the fit getters each frame rather than once inside the event
handler.

## Mobile readiness

On a phone, the browser takes space from your game: the address and tool
bars, the notch, the rounded corners, and the home indicator. The setup in
this section gives the game all of the space the phone leaves it. Both
`create-yage` templates already have the page setup. The Recommended template
also has a fullscreen button and can be installed to the Home Screen.

### Page setup

Let the page cover the whole screen with `viewport-fit=cover` in the viewport
tag:

```html
<meta
  name="viewport"
  content="width=device-width, initial-scale=1.0, viewport-fit=cover"
/>
```

Without it, iOS keeps the page inside a rectangle that avoids the notch and
the rounded corners, and paints the page background around it.

Then size the game's container to the visible screen and keep it clear of the
notch and the home indicator:

```css
#game {
  box-sizing: border-box;
  background: #0f172a; /* the renderer's backgroundColor */
  width: 100vw;
  height: 100vh; /* for browsers without dvh */
  height: 100dvh;
  padding: env(safe-area-inset-top) env(safe-area-inset-right)
    env(safe-area-inset-bottom) env(safe-area-inset-left);
}
```

- **Use `100dvh`, not `100vh`.** On a phone, `100vh` is the height with the
  browser's toolbars hidden. While the toolbars are showing, the bottom of a
  `100vh` game sits behind them. `100dvh` is the height the player can see.
- **Don't rely on scrolling to hide the toolbars.** Mobile Safari does not
  hide them reliably, and a game page does not scroll.
- **The safe-area padding keeps the game clear of the notch, the rounded
  corners, and the home indicator.** Each `env(safe-area-inset-*)` value is
  the size of what to avoid on that side, and `0` where there is nothing to
  avoid. The values are only non-zero with `viewport-fit=cover`.
  `RendererPlugin` sizes the canvas to the area inside the container's
  padding, so no renderer config is needed. This padding is the one place the
  insets are subtracted; a native shell draws the web view edge to edge and
  adds none of its own.
- **Give the container a background.** The padding shows the container's
  own background. In fullscreen the browser draws only the container, so a
  background set on `body` alone leaves black strips. Use the renderer's
  `backgroundColor`.

### Fullscreen button

A [fullscreen](#fullscreen) button gives the game the whole screen where the
browser allows it:

- **Put the button inside the renderer's `container`.** The renderer makes
  the container fullscreen, so a button inside it stays on screen to exit.
- **Hide the button where a request would do nothing.** One check covers
  every such case:

  ```typescript
  import type { RendererPlugin } from "@yagejs/renderer";

  declare const renderer: RendererPlugin;

  const button = document.getElementById("fullscreen")!;
  button.hidden = renderer.fullscreenSupport === "unsupported";
  ```

  `fullscreenSupport` is `"unsupported"` on iPhone, which cannot show a page
  fullscreen; in a frame from another origin without `allow="fullscreen"`; and
  in an installed app that already opens fullscreen, where the game fills the
  screen anyway.
- **Move focus off the button after a click.** Otherwise the button keeps
  focus, and a game key such as Enter presses it again. Call
  `button.blur()` in the click handler.
- **iPad Safari adds its own controls.** In fullscreen it shows an exit
  button over the page that the page cannot hide, and a swipe down exits
  fullscreen.

The Recommended template's `src/fullscreen.ts` is a complete button that
follows these rules and changes its label on `screen:fullscreen`.

### Rotate-device overlay

For a landscape game, ask for the orientation with `lockOrientation` where
`orientationLockSupport` allows it, and show an overlay asking the player to
turn the device when the result is portrait. Safari has no orientation lock,
and Chrome on Android locks only while the game is fullscreen or installed, so
the overlay is the fallback on most phones. Update it on the
`screen:orientation` event (see [Orientation](#orientation)), and read
`renderer.orientation` once after `engine.start()`, because the event fires
only on a change.

### Add to Home Screen

On iPhone, the only way to remove Safari's toolbars is for the player to add
the game to the Home Screen and open it from there. It then opens without
browser toolbars.

- **iOS has no install prompt.** Players use **Share → Add to Home Screen**
  in Safari. To help them, show your own instructions.
- **Before iOS 26, the page needs a web app manifest.** Since iOS 26, every
  site added to the Home Screen opens without toolbars. Earlier versions only
  do so when the manifest sets `display` to `"standalone"`. iOS does not
  support `"fullscreen"`. To also hide Android's status and navigation bars,
  add `display_override: ["fullscreen"]`, which iOS ignores.
- **`<link rel="apple-touch-icon" href="/apple-touch-icon.png">`** sets the
  Home Screen icon, 180×180 pixels.
- **`<meta name="apple-mobile-web-app-status-bar-style" content="black-translucent">`**
  lets the installed game draw under the status bar. The safe-area padding
  keeps the game clear of the clock and battery.

The Recommended template's production build has this manifest and these
tags. See
[Installable and offline](/getting-started/installation/#installable-and-offline-recommended-template).
To make another project installable, copy the Recommended template's
`VitePWA` entry in `vite.config.ts`, its icons in `public/`, and the icon and
status-bar tags in its `index.html`.
