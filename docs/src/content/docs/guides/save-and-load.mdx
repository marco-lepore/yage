title: "Save & Load"
description: "Typed reactive stores, save slots, and persistent game state"
---

YAGE saves explicit state roots. Use the built-in typed stores for settings,
save slots, world facts, and progression, or implement
`Serializable<TEncoded>` for a custom domain model. The save package does not
traverse scenes, entities, components, renderer resources, or callbacks.

## Why stores

Most save data isn't really "the simulator's runtime state" — it's the
*intentional* facts about the game: which chests are opened, what chapter the
player is on, the current settings, the inventory. Trying to serialize a live
component graph to capture that data is fragile (closures, runtime objects,
destroyed entities). A typed store says directly what the data *is*.

Stores also avoid the trap of accidentally persisting things you don't want —
particle positions, animation phase, transient UI state — because you choose
what each store contains.

## Creating reactive state

YAGE's state factories live in `@yagejs/core` and produce pure-data values
implementing three contracts: `Reactive` (subscribe), `Serializable<T>`
(serialize/hydrate), and `Resettable` (reset). The save layer consumes any
`Serializable<T>`; ids and versioning live at the save call site.

### Compound `createStore` (primary)

```typescript yage-group="save" yage-file="persistence/stores.ts"
// game/persistence/stores.ts
import { createStore } from "@yagejs/core";
import { save } from "./save.js";

export interface Potion { name: string; quality: number }

export const game = createStore((s) => ({
  inventory:  s.map<string, number>(),
  recipes:    s.set<string>(),
  gold:       s.counter({ default: 0 }),
  reputation: s.counter({ default: 50 }),
  shelf:      s.list<Potion>(),
  day:        s.value<number>({ default: 1 }),
  settings:   s.record<{ volume: number; lang: string }>({
    default: () => ({ volume: 0.8, lang: "en" }),
  }),
}));

// Idiomatic per-shape ops on each leaf:
game.gold.increment(10);
game.inventory.set("moonleaf", 3);
game.recipes.add("brew-1");
const potionId = game.shelf.add({ name: "Cure", quality: 7 });

// Save the whole tree as one document — id at the save call site:
save.autoPersist("game", game);
```

Leaf builder methods on `s`:

- `s.value<T>({ default, codec? })` — single typed cell.
- `s.counter({ default? })` — number with `value`, `set`, `increment`, `decrement`, `clamp(value, min, max)`.
- `s.record<T>({ default, codec? })` — object with shallow merge.
- `s.map<K, V>({ default? })` — key→value.
- `s.set<K>({ default? })` — keys.
- `s.list<T>({ default?, keyBy? })` — ordered list with stable monotonic ids. Pass `keyBy: (item) => string | number` to enable O(1) lookup by a domain key via `findId` / `getByKey` / `upsert`.

The compound bundles every leaf so they serialise/restore atomically as one
document. Reserved leaf keys — `subscribe`, `serialize`, `hydrate`, `reset`
— collide at construction time.

`useStore(compound)` returns the encoded snapshot of the whole tree; for
fine-grained subscriptions read individual leaves.

### Leaf factories (one-offs)

When a single primitive doesn't belong inside a larger tree, use the leaf
factories directly:

```typescript yage-group="save" yage-file="persistence/stores.ts"
import {
  createRecord, createValue, createCounter,
  createMap, createSet, createList,
} from "@yagejs/core";

export interface SettingsData {
  audio: { music: number; sfx: number };
  vsync: boolean;
}

export type RunData = {
  chapter: number;
  coins: number;
  inventory: string[];
  position: { x: number; y: number };
};

export const initialRun = (): RunData => ({
  chapter: 1, coins: 0, inventory: [], position: { x: 0, y: 0 },
});

export const settings = createRecord<SettingsData>({
  default: () => ({ audio: { music: 0.8, sfx: 1.0 }, vsync: true }),
});

// The run in progress. The save slots below store copies of it.
export const saves = createRecord<RunData>({ default: initialRun });

export const opened    = createSet<string>();
export const defeated  = createMap<string, number>();
export const restEpoch = createCounter();
export const day       = createValue<number>({ default: 1 });
export const journal   = createList<{ at: number; text: string }>();
```

Shape APIs (every value also exposes `subscribe(fn)`, `serialize()`,
`hydrate(raw)`, `reset()`):

- `createRecord<T>` / `s.record`: `get(): Readonly<T>`, `set(partial: Partial<T>)`, `delete(key)`.
- `createValue<T>` / `s.value`: `get(): T`, `set(v: T)`.
- `createCounter` / `s.counter`: `value()`, `set(n)`, `increment(by?)`, `decrement(by?)`, `clamp(value, min, max)`.
- `createMap<K, V>` / `s.map`: `get(k)`, `set(k, v)`, `delete(k)`, `has(k)`, `entries()`, `size()`, `clear()`.
- `createSet<K>` / `s.set`: `add(k)`, `delete(k)`, `has(k)`, `values()`, `size()`, `clear()`.
- `createList<T>` / `s.list`: `add(item): number` (id), `remove(id): boolean`, `get(id)`, `update(id, partial)`, `list()`, `size()`, `clear()`. With a `keyBy` option, also `findId(key)`, `getByKey(key)`, and `upsert(key, item): number` (replace if the key exists, else insert). Without `keyBy`, the keyed methods throw. A keyed list holds at most one item per key: `add`, `update`, and `upsert` throw if the result would share a key with another item, and `upsert` requires the item's own key to match (`keyBy(item) === key`).

#### Removing a key from a record

`set` can only overwrite a key, so a record used as an open-ended bag needs
`delete` to drop one — after it, `key in flags.get()` is false and the key is
gone from `serialize()` too. Deleting a key that isn't there changes nothing and
notifies nobody.

```typescript
import { createRecord } from "@yagejs/core";

const flags = createRecord<Record<string, string | number | boolean>>({
  default: () => ({}),
});

flags.set({ metMira: true });
flags.delete("metMira"); // gone from get() and from serialize()
```

`delete` accepts the keys of an index signature (as above) and any key declared
optional. On a fixed-shape record a required key is a compile error: `get()`
returns `Readonly<T>`, so removing a `hp: number` would leave `get().hp` typed
`number` but missing at runtime. For the same reason a fixed-shape record is not
assignable to an open-ended `ReactiveRecord<Record<string, V>>` — deleting
through that alias would sidestep the check.

#### Keyed lists (lookup by a domain field)

Inventories, registries, and similar collections often need "find or update the
entry for key X". Pass `keyBy` so the list maintains a key→id index:

```typescript
import { createList } from "@yagejs/core";

const inventory = createList<{ itemId: string; quantity: number }>({
  keyBy: (slot) => slot.itemId,
});

inventory.upsert("sword", { itemId: "sword", quantity: 1 }); // insert
inventory.upsert("sword", { itemId: "sword", quantity: 2 }); // replace in place

inventory.findId("sword");   // -> the stable id
inventory.getByKey("sword"); // -> { itemId: "sword", quantity: 2 }
inventory.getByKey("axe");   // -> undefined
```

The index is derived, not stored — saves load unchanged and the index rebuilds
on `hydrate`.

Keys are unique: a keyed list holds at most one item per derived key. `add`,
`update`, and `upsert` throw if the operation would leave two live items sharing
a key. `upsert(key, item)` is the add-or-replace-by-key operation, so it also
requires the item's own key to match the lookup key (`keyBy(item) === key`);
a mismatch throws.

Codecs are bundled for Set/Map/Counter/List — you only specify a custom
`codec` on `createRecord<T>` / `createValue<T>` (or the matching leaves)
when `T` contains exotic types.

### Migrating from many leaf factories to one compound

If your game grew a `createRecord` here, a `createCounter` there, and several
`createSet`s — each with its own `autoPersist` call — the compound collapses
them into one save target with atomic writes:

```typescript yage-group="save" yage-file="migrate-to-compound.ts"
import { createCounter, createRecord, createSet, createStore } from "@yagejs/core";
import { save } from "./persistence/save.js";

interface RunData { chapter: number; coins: number }

// Before — three save documents, three autoPersist calls.
const progression = createRecord<RunData>({ default: () => ({ chapter: 1, coins: 0 }) });
const deaths      = createCounter();
const flags       = createSet<string>();
save.autoPersist("run.progression", progression);
save.autoPersist("run.deaths", deaths);
save.autoPersist("run.flags", flags);

// After — one document, one autoPersist call, atomic serialize/hydrate.
const game = createStore((s) => ({
  progression: s.record<RunData>({ default: () => ({ chapter: 1, coins: 0 }) }),
  deaths:      s.counter({ default: 0 }),
  flags:       s.set<string>(),
}));
save.autoPersist("run", game);
```

## Creating the Save instance

Construct `Save` once in your entry point. The plugin only registers it under
`SaveServiceKey` for in-game DI access — boot-time work uses `save` directly.

```typescript yage-group="save" yage-file="persistence/save.ts"
// game/persistence/save.ts
import { createSave, localStorageAdapter } from "@yagejs/save";

export const save = createSave({
  adapter: localStorageAdapter({ namespace: "my-game" }),
});
```

```typescript yage-group="save" yage-file="main.ts"
// game/main.ts
import { Engine } from "@yagejs/core";
import { SavePlugin } from "@yagejs/save";
import { save } from "./persistence/save.js";
import { settings, saves } from "./persistence/stores.js";

await Promise.all([
  save.restore("settings", settings),
  save.restore("saves", saves),
]);
save.autoPersist("settings", settings);   // stream changes back to disk

const engine = new Engine();
engine.use(new SavePlugin({ save }));
await engine.start();
```

## Settings — single document + auto-persist

Settings change rarely and should write to disk on every change. `autoPersist`
subscribes to the value and writes on every change, coalescing multiple
synchronous `set` calls into one write per microtask.

```typescript yage-group="save" yage-file="settings.ts"
import { save } from "./persistence/save.js";
import { settings } from "./persistence/stores.js";

await save.restore("settings", settings);            // load on boot
const stop = save.autoPersist("settings", settings);

// Anywhere in the game…
settings.set({ audio: { ...settings.get().audio, music: 0.5 } });
// → one write fires after the current microtask
```

`stop()` removes the subscriber and cancels any pending write. For real
time-based debouncing across user interactions (e.g. throttling a slider
drag), wrap the value yourself.

`autoPersist` writes nothing to the console when a write fails. `save.flush()` waits for the
writes `autoPersist` started or scheduled before the call, and rejects with an
`AggregateError` naming the stores whose latest write failed — use it before
you tell the player their settings are saved. A failure nothing awaits becomes
an unhandled promise rejection, which the browser reports in the console. A
later successful write of the same store clears the failure.

```typescript yage-group="save" yage-file="flush.ts"
import { save } from "./persistence/save.js";

// The line the settings menu shows after the player presses "Save".
export async function settingsSaveMessage(): Promise<string> {
  try {
    await save.flush();
    return "Settings saved.";
  } catch {
    return "Your settings could not be saved. Please try again.";
  }
}
```

## Save slots

Slots are named instances of a value. Use them for "save game" semantics.
Each slot has optional metadata persisted alongside the value (timestamp,
location, thumbnail, anything you want).

```typescript yage-group="save" yage-file="slots.ts"
import { save } from "./persistence/save.js";
import { saves } from "./persistence/stores.js";

interface RunMeta {
  location: string;
  playtime: number;
}

await save.saveSlot<unknown, RunMeta>("saves", "manual-1", saves, {
  metadata: { location: "Forest Temple", playtime: 60 },
});

await save.loadSlot("saves", "manual-1", saves);

const slots = await save.listSlots<RunMeta>("saves");
// newest first: [{ name: "manual-1", savedAt: 1714…, metadata: {…} }, …]

await save.deleteSlot("saves", "manual-1");
```

Each slot is one document holding the value, the time it was written and the
metadata, so saving or deleting a slot is a single storage operation.
`listSlots` returns the store's slots newest first; it reads every slot
document of that store, so a store with many large slots takes longer to list
than to load one. A slot whose stored bytes are damaged is left out of the
listing and left in storage.

`loadSlot` throws `SlotNotFoundError` for missing slots, and
`CorruptPayloadError` when the stored bytes are not readable as a save.

Operations on one slot take effect in the order you call them, whether or not
you await them. A `loadSlot` called right after an unawaited `saveSlot`
or `deleteSlot` of the same slot reads its result.

### How long a slot name can be

`Save` stores each slot under a key of at most 96 bytes, on every adapter, so
a slot name that works in a web build also works in a packaged one. A longer
key throws `InvalidKeyError`, naming the store id and the slot name, before
anything is written.

A slot's key is the store id, 3 bytes of separators, then the slot name. The
store id and the slot name are URI-encoded:

- `A-Z`, `a-z`, `0-9` and `- _ . ! ~ * ' ( )` take 1 byte each.
- Any other character takes 3 bytes per byte of its UTF-8 form: 3 for a space
  or `/`, 6 for `é`, 9 for most Chinese, Japanese and Korean characters, and
  12 for an emoji.

With the store id `saves`, a slot name holds 88 ASCII letters or 9 Japanese
characters. A document saved with `persist` or `autoPersist` has a key of the
store id and 2 bytes, so its store id takes up to 94 bytes once encoded.

### Continue (load latest)

```typescript yage-group="save" yage-file="continue.ts"
import { save } from "./persistence/save.js";
import { saves } from "./persistence/stores.js";

const [latest] = await save.listSlots("saves");
if (latest) {
  await save.loadSlot("saves", latest.name, saves);
}
```

### Multi-profile

If you have profiles (per-user save banks), use hierarchical slot names with
the `prefix` filter:

```typescript yage-group="save" yage-file="profiles.ts"
import { save } from "./persistence/save.js";
import { saves } from "./persistence/stores.js";

const profile = "alice"; // the active profile's name
await save.saveSlot("saves", `${profile}/manual-1`, saves);
const profileSlots = await save.listSlots("saves", { prefix: `${profile}/` });
```

The engine doesn't formalize profile scopes — the convention lives in your
game code, which keeps the primitive simple.

## In-game access via DI

Components and scenes resolve the registered Save instance through
`SaveServiceKey`:

```typescript yage-group="save" yage-file="checkpoint.ts"
import { Component, defineEvent } from "@yagejs/core";
import { SaveServiceKey } from "@yagejs/save";
import { saves } from "./persistence/stores.js";

const Rested = defineEvent("rested");

class CheckpointOnRest extends Component {
  onAdd() {
    this.listen(this.entity, Rested, async () => {
      const save = this.use(SaveServiceKey);
      await save.saveSlot("saves", "auto", saves);
    });
  }
}
```

## Migration & versioning

`version` + `migrate` live on the read call (`restore` / `loadSlot`), not on
the primitive; `autoPersist` takes `version` only. Bump `version` when the
encoded shape changes and pass `migrate` to transform older payloads. Per-leaf
migration inside a compound is not supported — migrate the tree as a whole.

```typescript yage-group="save" yage-file="migration.ts"
import { createRecord, createStore } from "@yagejs/core";
import { save } from "./persistence/save.js";
import { initialRun, type RunData } from "./persistence/stores.js";

// Single record — migrate the record value.
const saves = createRecord<RunData>({ default: () => initialRun() });
await save.restore("saves", saves, {
  version: 3,
  migrate: (old, fromVersion) => {
    let v = old as Record<string, unknown>;
    if (fromVersion < 2) v = { ...v, inventory: [] };
    if (fromVersion < 3) v = { ...v, position: v.startPos ?? { x: 0, y: 0 } };
    return v as RunData;
  },
});

// Compound — one migrate on the tree. Returns the new encoded form each
// leaf consumes: `{ gold: number, day: { value: number } }` here.
const game = createStore((s) => ({
  gold: s.counter({ default: 0 }),
  day:  s.value<number>({ default: 1 }),
}));
await save.restore("run", game, {
  version: 2,
  migrate: (old) => {
    const v1 = old as { gold: number };
    return { gold: v1.gold, day: { value: 7 } };
  },
});
```

Newer-than-current payloads throw `StoreVersionTooNewError`; older payloads
without a `migrate` throw `StoreMigrationMissingError`.

## Codecs

Stores serialize via a `Codec<T, TEncoded>`. `TEncoded` defaults to `T` for
identity codecs, and surfaces in `serialize()`/`hydrate()` and
`RestoreOptions.migrate` so migrations get the right type. Built-ins:

```typescript
import type { Codec } from "@yagejs/core";

// Built-in codecs exported by @yagejs/core:
declare function jsonCodec<T>(): Codec<T, T>;                 // identity (default)
declare function setCodec<K>(): Codec<Set<K>, K[]>;
declare function mapCodec<K, V>(): Codec<Map<K, V>, [K, V][]>;
declare function dateCodec(): Codec<Date, string>;            // ISO string
```

`createSet`/`createMap`/`createCounter`/`createList` bundle the right codec —
you only specify a codec for `createRecord<T>` / `createValue<T>` (or the
matching `s.record`/`s.value` leaves) when the type contains exotic values.
When a custom codec changes the encoded shape (e.g. `Date → string`), pass
both generics so the change shows up in `serialize()` and `migrate` return
types: `createValue<Date, string>({ default: () => new Date(), codec: dateCodec() })`.

## Adapters

An adapter is where the bytes go. Three ship with the package, and
`@yagejs/host-electron` adds `electronSaveAdapter()` for a desktop build: a
`fileAdapter` over the app's data directory, running in Electron's main
process, so a page that crashes during a save does not stop the write. See
[Desktop with Electron](/guides/electron/).

`@yagejs/host-capacitor` adds `capacitorSaveAdapter({ profile })` for a
mobile build: a `fileAdapter` over a directory in the app's private Library
directory, one per build profile. A write that resolved is held when the
system kills the app. See [Mobile with Capacitor](/guides/capacitor/).

```typescript
import type { SaveAdapter, SaveFileStore } from "@yagejs/save";

// Adapter factories exported by @yagejs/save:
// browser
declare function localStorageAdapter(opts?: { namespace?: string }): SaveAdapter;
// tests + Node
declare function memoryAdapter(): SaveAdapter;
// any directory of files, including one reached over a native bridge
declare function fileAdapter(opts: { store: SaveFileStore }): SaveAdapter;
```

The interface is four async string operations — `read`, `write`, `delete`,
`list` — and a promise about what happens to each key:

- **Replacing a key is all-or-nothing.** If a write is cut off, a later read
  gives you the value that was there before, or the new one. Never a mix.
- **A resolved write is stored.** Every later `read` and `list` sees it, and
  it is still there if the process is killed a moment later. `memoryAdapter`
  and `localStorageAdapter` do not keep that last promise; the table below
  says what they keep.
- **Operations on one key keep their order.**
- **A write that cannot finish rejects** and leaves the key readable.

Two keys are never written together, so state that has to agree belongs in one
compound store, which `createStore` already saves as one document.

What each adapter survives:

| Adapter                                                | Process kill                                                                     | Power loss                       |
| ------------------------------------------------------ | -------------------------------------------------------------------------------- | -------------------------------- |
| `memoryAdapter`                                        | no — the values live in the process                                              | no                               |
| `localStorageAdapter`                                  | the browser commits on its own schedule, so the last writes can be lost, never torn | the browser's                    |
| `fileAdapter` over a store whose `write` syncs         | yes                                                                              | where the sync reaches the drive |
| `fileAdapter` over a store whose `write` does not sync | yes                                                                              | not guaranteed                   |

### Files

`fileAdapter` turns a directory of files into an adapter with those
guarantees, even when the file system has no atomic replace. You supply four
file operations; a `write` that an interruption cuts in half is expected and
handled. Each value is written to a shadow file first and carries a checksum,
so an interrupted write leaves the previous value or the new one readable.

```typescript yage-group="files"
import { createSave, fileAdapter } from "@yagejs/save";
import type { SaveFileStore } from "@yagejs/save";

const files = new Map<string, string>();
const store: SaveFileStore = {
  async read(name) {
    return files.get(name) ?? null;
  },
  async write(name, content) {
    files.set(name, content);
  },
  async delete(name) {
    files.delete(name);
  },
  async list() {
    return [...files.keys()];
  },
};

export const save = createSave({ adapter: fileAdapter({ store }) });
```

Keys are at most 96 bytes in UTF-8, which keeps the longest file name at 160
characters. `Save` refuses a longer key on every adapter; see
[How long a slot name can be](#how-long-a-slot-name-can-be). A file is named
`k-` plus the key in base32, so names hold only `a-z`, `2-7`, `-` and `.`.

A custom adapter — IndexedDB, cloud sync, your own shell — has to meet the
same four promises.

## When a save is finished

A resolved `persist`, `saveSlot` or `deleteSlot` means the storage holds the
value and every later read sees it. One document is the unit that changes
atomically; nothing spans two.

Whether a value survives the power going out is the storage's promise, not the
engine's. The table above says which adapter gives it.

Keep one `Save` per storage. Two instances, or two browser tabs writing the
same keys, are not coordinated.

A save is plain JSON that anyone with the device's files or the browser
profile can read. Keep passwords and tokens out of it.

## Saving when the game goes to the background

`@yagejs/save` does not save by itself when the app is backgrounded.
`autoPersist` already writes within a microtask of every change, and only your
game knows what its checkpoint is. Save it from the lifecycle event:

```typescript yage-group="save" yage-file="background.ts" yage-context="engine"
import { save } from "./persistence/save.js";
import { saves } from "./persistence/stores.js";

engine.events.on("host:active", ({ active }) => {
  if (!active) void save.saveSlot("saves", "auto", saves);
});
```

The operating system may end the process before that write resolves. The
previous checkpoint is still readable then, and the next launch restores it —
no shutdown callback is needed.

## Moving saves to another adapter

A packaged app and a web build never share storage, so a packaged release that
ships its own adapter from the start has nothing to import. If a shipped
release changes adapter, copy the keys at boot, before any save:

```typescript yage-group="move"
import type { SaveAdapter } from "@yagejs/save";

const DONE = "imported";

export async function importSaves(
  from: SaveAdapter,
  to: SaveAdapter,
): Promise<void> {
  if ((await to.read(DONE)) !== null) return;
  for (const key of await from.list("")) {
    const value = await from.read(key);
    if (value !== null) await to.write(key, value);
  }
  await to.write(DONE, new Date().toISOString());
}
```

The marker holds no `/`, so it cannot collide with a key `Save` writes.
Nothing is deleted from the source, so an interrupted copy runs again at the
next boot.

## Tests

Construct fresh state per test, swap in `memoryAdapter`:

```typescript
import { expect, it } from "vitest";
import { createRecord } from "@yagejs/core";
import { createSave, memoryAdapter } from "@yagejs/save";

const save = createSave({ adapter: memoryAdapter() });

it("round-trips a record", async () => {
  const settings = createRecord({ default: () => ({ music: 0.8, sfx: 1.0 }) });
  settings.set({ music: 0.3 });
  await save.persist("settings", settings);

  const next = createRecord({ default: () => ({ music: 0.8, sfx: 1.0 }) });
  await save.restore("settings", next);
  expect(next.get().music).toBe(0.3);
});
```

## Per-frame updates: don't

Stores are for *intentional* state — settings, slots, world facts. They notify
all subscribers synchronously on every change, and any UI bindings re-render.
**Don't update stores from `update(dt)` or other per-frame paths**; that's
what ECS state and `useQuery` / `useSceneSelector` are for. If you find
yourself debouncing every `set`, you're using the wrong primitive.

## Custom state roots

When a domain model does not fit a built-in store, implement
`Serializable<TEncoded>` directly. `serialize()` must return the complete
durable representation, and `hydrate()` must replace the model with that
representation. Pass the object to the same `persist`, `restore`, `saveSlot`,
and `loadSlot` methods shown above.

Live engine objects are not state roots. Save stable game facts such as entity
kind, position, health, inventory, quest progress, and scene identity, then let
normal scene setup reconstruct the corresponding runtime objects after load.
