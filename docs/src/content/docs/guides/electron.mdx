---
title: "Desktop with Electron"
description: "Ship a YAGE game as a desktop app: window state, fullscreen, file saves, and a locked-down shell"
---

`@yagejs/host-electron` runs a YAGE game as a desktop app. The window's
state reaches the engine, fullscreen is the window's whatever started it, and
saves are files in the app's data directory rather than browser storage.

A desktop build has two halves. The **shell** is the Electron app around the
game: its main script, its preload script and its window. The **page** is the
game's web page inside that window. This package holds both, so the window's
code is one call rather than a file every project copies.

## Install

```sh
npm install @yagejs/host-electron
npm install --save-dev electron@^44.7.0
```

`electron` is a peer dependency with the range `^44.7.0`.

## The game's entry file

Write one boot function for every target, and one entry file per target that
hands it the plugins that target needs.

```ts yage-group="targets" yage-file="boot.ts"
import { Engine } from "@yagejs/core";
import type { Plugin } from "@yagejs/core";
import { RendererPlugin } from "@yagejs/renderer";
import { SavePlugin, createSave } from "@yagejs/save";
import type { SaveAdapter } from "@yagejs/save";

export interface BootOptions {
  hostPlugins: readonly Plugin[];
  saveAdapter: SaveAdapter;
}

export async function boot(options: BootOptions): Promise<Engine> {
  const engine = new Engine();
  for (const plugin of options.hostPlugins) engine.use(plugin);
  engine.use(new RendererPlugin({ width: 640, height: 360 }));
  engine.use(
    new SavePlugin({ save: createSave({ adapter: options.saveAdapter }) }),
  );
  await engine.start();
  return engine;
}
```

The Electron entry installs the plugin and the save adapter without asking
whether the shell is there:

```ts yage-group="targets" yage-file="main.electron.ts"
import { ElectronHostPlugin, electronSaveAdapter } from "@yagejs/host-electron";
import { boot } from "./boot.js";

await boot({
  hostPlugins: [new ElectronHostPlugin()],
  saveAdapter: electronSaveAdapter(),
});
```

The browser entry installs neither:

```ts yage-group="targets" yage-file="main.web.ts"
import { localStorageAdapter } from "@yagejs/save";
import { boot } from "./boot.js";

await boot({
  hostPlugins: [],
  saveAdapter: localStorageAdapter({ namespace: "my-game" }),
});
```

With one page per target, a wrong build fails at start: open the Electron
build in a browser and it stops with a message naming the missing shell,
rather than running with the wrong saves.

### One bundle for every target

A project that ships a single bundle asks at run time instead.
`isElectronHost()` lives in its own entry that imports nothing, so a browser
build can call it before it loads the rest of the package.

```ts yage-group="single-bundle"
import { isElectronHost } from "@yagejs/host-electron/detect";
import { localStorageAdapter } from "@yagejs/save";
import type { Plugin } from "@yagejs/core";
import type { SaveAdapter } from "@yagejs/save";

let hostPlugins: readonly Plugin[] = [];
let saveAdapter: SaveAdapter = localStorageAdapter({ namespace: "my-game" });
if (isElectronHost()) {
  const host = await import("@yagejs/host-electron");
  hostPlugins = [new host.ElectronHostPlugin()];
  saveAdapter = host.electronSaveAdapter();
}
```

The drawback: a shell whose preload script failed to load looks like a browser
to the predicate. The game starts anyway and writes its saves to the browser's
storage, where the next release will not find them.

## The shell's main script

```ts yage-group="shell"
import { app } from "electron";
import { join } from "node:path";
import { startGame } from "@yagejs/host-electron/main";

startGame({
  webDir: join(app.getAppPath(), "dist-electron"),
  appId: "dev.example.mygame",
  // A packaged app is a release; electron-forge start runs unpackaged.
  profile: app.isPackaged ? "release" : "development",
  devTools: !app.isPackaged,
  externalLinks: ["https://example.dev/", "mailto:support@example.dev"],
  window: { width: 1280, height: 720, title: "My Game" },
}).catch((error: unknown) => {
  console.error(error);
  app.exit(1);
});
```

Call `startGame` once, at the top of the main script, before the app is ready.
It registers the scheme the page is served from before it returns, and
Electron accepts that registration only before the app is ready. Do not call
`protocol.registerSchemesAsPrivileged` in your shell: Electron accepts one
registration, and `startGame` makes it.

`startGame` resolves with the `BrowserWindow` after the page has loaded, so
the shell can add a menu or its own listeners. Every failure rejects the
promise it returns, an invalid option included, so the `catch` above handles
each one.

`preload.cjs` ships beside `main.js` in the installed package, and the window
loads it from there. The Forge configuration from `@yagejs-tools/pack` keeps
that directory in the archive.

`npx yage-pack init --target electron` writes this script and a Forge
configuration beside it; see
[Packaging for desktop and mobile](/tooling/packaging/).

## What `startGame` sets up

- **The game's files.** `webDir` is served from `yage://game`. A path that
  leads outside the directory is refused. The directory may be an archive.
- **A content security policy** on every response, described below.
- **Permissions.** The page gets what a browser tab gives without a prompt:
  fullscreen, pointer lock, keyboard lock and sanitized clipboard writes. Add
  more with `permissions`. Everything else is denied, including any request
  that did not come from the game page.
- **Links.** `window.open(url)` opens no window of its own. It passes the URL
  to the system browser or mail client when one of `externalLinks` allows it,
  as described below. The game page never navigates away from `yage://game`.
- **One copy of the app.** A second launch quits at once and brings the first
  window forward. Two copies would write the same save directory out of order.
- **Closing.** `window.close()` from the game closes the window and ends the
  app, so a Quit button needs nothing else. A browser tab ignores
  `window.close()`, so show Quit only in the build your Electron entry starts.
- **The menu.** On macOS: Quit, the text-field commands and the window
  commands. Elsewhere: no menu bar. With `devTools: true` Electron's default
  menu stays, which offers Reload and Toggle Developer Tools.
- **No remote debugging in a packaged app.** Chromium's
  `--remote-debugging-port` and `--remote-debugging-pipe` switches let another
  program inspect and control the page, even with `devTools: false`. No
  release setting turns them off. A packaged app started with either switch
  does not load the game: `startGame` rejects and opens no window. Chromium
  may already have opened the port by then, so the refusal stops the game from
  loading, not the port from opening. `electron-forge start` runs unpackaged
  and accepts both switches.

### Which links open

Each entry in `externalLinks` allows a part of one site, or one mail address:

| Entry | Allows |
| ----- | ------ |
| `"https://example.dev"` | every page of `https://example.dev` |
| `"https://example.dev/docs"` | `/docs` and the pages under it, such as `/docs/guide`, but not `/docs-private` |
| `"mailto:support@example.dev"` | a mail to that address alone, with no subject, body, `cc` or `bcc` |

A web link opens when it has the entry's scheme, host and port and its path is
the entry's path or lies under it. `/docs` and `/docs/` are the same entry,
and the link may carry any query or hash. The host is compared after
`startGame` reads the entry as a URL, so `https://Example.dev/` works, and a
look-alike such as `https://example.dev.other.test/` or
`https://example.dev@evil.test/` does not match.

`startGame` rejects these entries and names each one:

- a web entry with a user name, a password, a query or a hash
- a bare `"mailto:"`
- a `mailto` entry with a query

## Configuration

| Option | Default | Meaning |
| ------ | ------- | ------- |
| `webDir` | required | Absolute path of the built web directory, which may lie inside an archive. It must hold an `index.html`. |
| `appId` | required | The app's stable identifier, matching `^[A-Za-z0-9][A-Za-z0-9.-]*$`. Names the save directory. |
| `profile` | required | The build profile, matching `^[a-z][a-z0-9-]*$`. Test and release saves never mix. |
| `window` | Electron's defaults | Size, title and look. Web preferences, `show` and `simpleFullscreen` stay the shell's. |
| `externalLinks` | none | Links `window.open` may open outside the app: an `http` or `https` site path, or a `mailto` address. See [Which links open](#which-links-open). |
| `permissions` | none | Permission names granted beyond the four above. |
| `contentSecurityPolicy` | `DEFAULT_CONTENT_SECURITY_POLICY` | Replaces the policy every response carries. |
| `devTools` | `false` | Developer tools and Electron's default menu. |
| `query` | `""` | Appended to the page's URL; empty or starting with `?`. |

An option the shell cannot use rejects the promise `startGame` returns, naming
the option and the value, before anything is registered.

## The content security policy

`DEFAULT_CONTENT_SECURITY_POLICY` allows the engine what the engine uses and
nothing more: WebAssembly for physics and layout, a worker from a blob for
image decoding, a `data:` fetch for the layout library's bundled WebAssembly,
and inline style for the canvas and the element that reports the scene to a
screen reader.

`script-src` has no `'unsafe-eval'`, so no script in the page can turn a
string into code. PixiJS writes shader and uniform code at run time, and
`RendererPlugin` handles that itself: on such a page it loads PixiJS's
prebuilt replacements before it creates the Pixi application. Your game needs
no import and no option for it.

Pass your own `contentSecurityPolicy` when the game loads something from
another origin, or when it asks for WebGPU and uses `motionBlur` from
`@yagejs/effects`. Under a policy without `'unsafe-eval'`, PixiJS on WebGPU
writes integer uniforms as floats and that filter draws nothing. The renderer
asks for WebGL first, and WebGL draws it correctly.

## What the game gets

### Who is running it

`engine.host.info` reports `runtime: "electron"`, the operating system, the
app's version from the shell directory's `package.json`, and Electron's own
version. Electron has no build number, so `appBuild` is `undefined`.

Read these for a crash report or a diagnostics screen. Branch on capability
instead: `renderer.fullscreenSupport`, `renderer.orientationLockSupport` and
the other support values say what this host can do, and they keep working when
the same game runs in a browser or on a phone.

### Window state

`engine.host.lifecycle` reports three fields, all from the main process:

- `visibility` is `"visible"` while the window is shown and not minimised. The
  page's own visibility is not used, because it stays `"visible"` behind a
  minimised window.
- `focus` is the window's keyboard focus.
- `activity` is `"inactive"` while the screen is locked or the machine is
  suspended, and `"active"` once neither holds. It reads `"unknown"` until the
  first such event, because nothing reports the lock state at launch.

`engine.host.active` is `false` while the window is unfocused. Audio pauses
then, because `audio.autoPause` is on by default, and held keys and buttons
are released. Scenes pause only when the game sets
`engine.scenes.autoPause = true`. A game that should keep running behind
another window sets `engine.host.activeWhenUnfocused = true`.

A window another window covers still counts as visible: Electron reports no
occlusion.

### Fullscreen

`renderer.isFullscreen` is the window's state, whatever put it there — the
menu, the system button, or the game's own
`renderer.requestFullscreen()`. The renderer emits one `screen:fullscreen`
event per change.

A request resolves once the window reports the change, or rejects after 3000 ms
with `ElectronHostPlugin: the window did not enter fullscreen within 3000 ms.`
Electron reports no refusal of its own, so the bound is how a request the
system ignored ends.

On macOS, Escape does not leave a fullscreen window. Bind it to
`renderer.exitFullscreen()` if your game wants that.

`renderer.orientationLockSupport` is `"unsupported"`: a desktop window cannot
lock the screen orientation.

### Saves

`electronSaveAdapter()` writes each key as a file under
`<appData>/<appId>/saves/<profile>`. The directory follows `appId`, not the
app's display name, so renaming the app keeps the player's saves.

The write runs in the main process, so a page that crashes mid-save does not
stop it. On macOS each write reaches the drive before it resolves, so a save
that resolved survives a power cut. An interrupted write leaves the previous
value or the new one readable, never a damaged one.

The limits: a key is at most 96 bytes in UTF-8, and one value at most
67,108,864 UTF-16 code units.

Main-process code can read the same files, for a backup command or an "open
save folder" menu item:

```ts yage-group="shell-saves"
import { fileAdapter } from "@yagejs/save";
import { nodeFileStore, saveDirectory } from "@yagejs/host-electron/main";

const directory = saveDirectory({
  appId: "dev.example.mygame",
  profile: "release",
});
const adapter = fileAdapter({ store: nodeFileStore(directory) });
const stored = await adapter.list("");
```

### Audio

Audio starts without a user gesture. Electron's autoplay policy asks for none,
so a game can play music from its first frame.

## Errors you may see

The page talks to the shell through one object the preload script exposes,
with a protocol number. Each page entry checks it before anything else, and
reports what to do:

- **No bridge.** `ElectronHostPlugin.install: no YAGE host bridge on this page.
  Load the game in a shell that runs the @yagejs/host-electron preload script,
  or leave this plugin out of a browser build.` The build ran in a browser, or
  the shell's preload script did not load.
- **Another protocol.** `ElectronHostPlugin.install: the shell speaks host
  bridge protocol 2 and this game was built with protocol 1. Build the shell
  and the game with the same @yagejs/host-electron version.` The shell and the
  game were built against different versions of this package.

`electronSaveAdapter` reports the same cases under its own name. The check runs
before the plugin attaches anything, so `engine.start()` rejects and the engine
stops.

`startGame` rejects with its own: calling it twice, calling it after the app
is ready, a `webDir` that is not an absolute path or holds no `index.html`, an
`appId` or `profile` a directory name cannot hold, an external link that is
not an `http`, `https` or `mailto` URL or breaks the rules in
[Which links open](#which-links-open), a `query` that does not start with a
question mark, window options that set `simpleFullscreen`, and a packaged app
started with `--remote-debugging-port` or `--remote-debugging-pipe`.

An `ElectronHostPlugin` belongs to one engine. Installing an instance whose
engine was destroyed throws `ElectronHostPlugin.install: this instance belongs
to a destroyed engine. Construct a new ElectronHostPlugin for each engine.`
