## Creating an Engine

The `Engine` is the top-level object that owns the game loop, scene stack, and
service container. Pass an options object to configure it:

```typescript
import { Engine } from "@yagejs/core";

const engine = new Engine({
  debug: true,
  fixedTimestep: 1 / 60, // ~0.0167 s (default)
  maxFixedStepsPerFrame: 5,  // spiral-of-death protection
});
```

| Option | Default | Purpose |
|---|---|---|
| `debug` | `false` | Publish `window.__yage__` for the browser console and test drivers. Its `inspector` comes from `DebugPlugin` or `InspectorPlugin` — see [The Inspector](/guides/debug/#the-inspector) |
| `fixedTimestep` | `1 / 60` | Seconds per fixed-update tick |
| `maxFixedStepsPerFrame` | `5` | Cap on fixed-update iterations per frame |

Errors thrown inside code the engine calls on your behalf are reported and
rethrown — see [Errors](/guides/debug/#errors).

## Engine Lifecycle

The three-step lifecycle is intentionally simple:

```typescript yage-context="engine"
import { RendererPlugin } from "@yagejs/renderer";
import { PhysicsPlugin } from "@yagejs/physics";
import { InputPlugin } from "@yagejs/input";

// 1. Register plugins
engine.use(new RendererPlugin({ width: 800, height: 600, container: document.getElementById("game")! }));
engine.use(new PhysicsPlugin());
engine.use(new InputPlugin());

// 2. Start the loop
await engine.start();

// 3. Tear down when done
engine.destroy();
```

`engine.use()` accepts plugins in any order — the engine resolves the correct
initialization order automatically. `engine.start()` is async because some
plugins need to load external resources (e.g. the Rapier WASM binary).

### An engine runs once

`destroy()` is permanent. Afterwards `start()` and `use()` throw, and further
`destroy()` calls do nothing, so a host that tears down defensively (hot
reload, a component unmounting) can call it without tracking whether it already
did. Create a new `Engine` when you need to run again: plugins release
resources they cannot rebuild, so the same instance cannot be restarted.

A `start()` that rejects is terminal in the same way. Plugins installed before
the failure already hold their services, and the container refuses to register
those twice, so a retry would fail on the duplicate rather than on the original
problem. Call `destroy()` to release what did install, then build a new engine.

Calling `destroy()` while `start()` is still awaiting a plugin cancels the rest
of startup — the loop never starts and no further plugin hook runs.

Restarting the *game* is a different operation, and the engine stays up for it.
Reset the scene stack instead:

```typescript yage-context="engine"
import { Scene } from "@yagejs/core";

class GameScene extends Scene {
  readonly name = "game";
}

class MenuScene extends Scene {
  readonly name = "menu";
}

// Restart the level
await engine.scenes.replace(new GameScene());

// Or drop the whole stack and start from the menu
await engine.scenes.popAll();
await engine.scenes.push(new MenuScene());
```

Scene changes requested after `destroy()` are ignored. In development builds
the scene manager logs a warning naming the call it dropped.

## The Plugin Interface

A plugin is a plain object that implements the `Plugin` interface:

```typescript
import {
  Plugin,
  EngineContext,
  Phase,
  ServiceKey,
  System,
  SystemScheduler,
} from "@yagejs/core";

class MyService {
  spritesDrawn = 0;
}

const MyServiceKey = new ServiceKey<MyService>("my-plugin:service");

class MySpriteSystem extends System {
  readonly phase = Phase.Render;

  update(): void {
    // draw the plugin's sprites and count them on MyService
  }
}

const myPlugin: Plugin = {
  name: "my-plugin",
  version: "1.0.0",
  dependencies: ["renderer"], // other plugin names this depends on

  install(context: EngineContext) {
    // Register services into the DI container
    context.register(MyServiceKey, new MyService());
  },

  registerSystems(scheduler: SystemScheduler) {
    // Add systems to the game loop
    scheduler.add(new MySpriteSystem());
  },

  onStart() {
    // Called after the loop has started and all plugins are wired
  },

  onDestroy() {
    // Cleanup: dispose GPU resources, close connections, etc.
  },
};
```

Every field except `name` and `version` is optional. A minimal plugin is
`{ name: "hello", version: "1.0.0" }`.

The scheduler also reports where the current call is executing, for plugin
code that can be reached from more than one phase:

```typescript yage-context="context"
import { SystemSchedulerKey } from "@yagejs/core";

const scheduler = context.resolve(SystemSchedulerKey);

scheduler.currentPhase;   // the Phase running right now, or null outside any phase
scheduler.fixedStepIndex; // monotonic count of fixed steps started — a frame can
                          // run several fixed steps, or none
```

`@yagejs/input` reads these to scope its edge queries to the caller's frame or
fixed step; any plugin whose behavior depends on its execution context can
branch on them the same way.

## Plugin Lifecycle Order

When `engine.start()` is called the engine processes plugins in this sequence:

1. **`install(context)`** — register services and configuration into the DI
   container. Runs for every plugin before any systems are added.
2. **`registerSystems(scheduler)`** — add systems to the scheduler. All
   services from step 1 are available.
3. **System wiring** — every `scheduler.add()` keeps its phase sorted by
   priority, at startup and at runtime.
4. **Loop starts** — frames begin to run. `RendererPlugin` connects the loop
   to the PixiJS application's ticker, so with a renderer the ticker drives
   each frame. Without a renderer, the loop requests its own frames with
   `requestAnimationFrame` in a browser.
5. **`onStart()`** — called once the first frame is queued. Safe to spawn
   entities, push scenes, and interact with the full engine.
6. **Game runs** — the loop calls systems each frame.
7. **`onDestroy()`** — called by `engine.destroy()` for every plugin whose
   `install()` was called, in reverse install order.

## Plugin Configuration

Built-in plugins accept configuration via their constructor:

```typescript yage-context="engine"
import { RendererPlugin } from "@yagejs/renderer";
import { PhysicsPlugin } from "@yagejs/physics";

engine.use(
  new RendererPlugin({
    width: 1280,
    height: 720,
    backgroundColor: 0x1a1a2e,
    container: document.getElementById("game")!,
  }),
);

engine.use(
  new PhysicsPlugin({
    gravity: { x: 0, y: 980 },
  }),
);
```

## Dependency Resolution

Plugins declare dependencies by name. The engine performs a topological sort
before running the lifecycle so that a plugin's dependencies are always
installed first:

```typescript
import type { Plugin } from "@yagejs/core";

const uiPlugin: Plugin = {
  name: "ui",
  version: "1.0.0",
  dependencies: ["renderer", "input"],
  // ...
};
```

If a dependency is missing the engine throws at startup with a clear message
listing the unresolved names. Circular dependencies are also detected and
reported.

Install order is not registration order. Plugins that declare no
dependencies install first, in the order they were registered. A plugin with
dependencies installs after all of them, even when you registered it first. So
`DebugPlugin`, which depends on the renderer, installs after `InputPlugin` and
`PhysicsPlugin` wherever you register it.

A plugin that uses a service another plugin provides, without depending on it,
resolves that service in `onStart` rather than `install`: by then every plugin
has installed. `RendererPlugin` publishes its render facet to the Inspector this
way, since the Inspector usually comes from `DebugPlugin`.

## The Host

The host is the application that runs the game's page: a browser tab, or a
native shell built around a web view. Every engine has a `Host` that names it,
as `engine.host` and under `HostKey`:

```typescript yage-context="engine"
const info = engine.host.info;
if (info.runtime !== "browser") {
  console.log(`${info.runtime} ${info.os} app ${info.appVersion}`);
}
```

Inside a component, resolve the same object through the key:

```typescript
import { Component, HostKey } from "@yagejs/core";

class BuildLabel extends Component {
  text = "";

  onAdd(): void {
    const { runtime, os, appVersion } = this.use(HostKey).info;
    this.text = `${runtime} on ${os}, version ${appVersion ?? "unknown"}`;
  }
}
```

`info` is for display and diagnostics, such as this label or a log line. What
the game offers follows the support values, such as
`renderer.fullscreenSupport`, which keep working when the same game runs in a
browser.

A page with no host adapter reports `runtime: "browser"`, `os: "unknown"`, and
`undefined` for `appVersion`, `appBuild` and `runtimeVersion`. The operating
system is `"unknown"` in a browser because a page reads the system name only
from the user agent, and an emulated device changes that string. `undefined` in
a version field means the host has no authoritative value to report.

`engine.host.info` always holds all five fields. An adapter supplies a
`HostInfoInput`, where `runtime` and `os` are required and the three versions
are optional, so a shell that knows only its app version leaves the other two
out.

`runtime` is a plain string rather than a fixed set of names, so an adapter you
write names itself. `os` is one of `"macos"`, `"windows"`, `"linux"`, `"ios"`,
`"android"` and `"unknown"`.

### Active, visible, focused

The host also reports what the application is doing. Three states, each
`"unknown"` where the host cannot observe it:

| State        | What it says                                                                         |
| ------------ | ------------------------------------------------------------------------------------ |
| `activity`   | Whether the operating system runs the app in the foreground and delivers input to it |
| `visibility` | Whether the player can see the game's page                                           |
| `focus`      | Whether the game's window has keyboard focus                                         |

`engine.host.active` combines them into the one answer the engine follows: it is
`false` while the app is inactive, the page is hidden, or the window is
unfocused. `"unknown"` never makes the host inactive. Scenes follow it through
`scenes.autoPause`, audio through `audio.autoPause`, and input releases held
keys, buttons and touches whenever one of the three states turns negative.

```typescript yage-context="engine"
engine.host.lifecycle.visibility; // "visible" | "hidden" | "unknown"
engine.host.active; // false while the game is in the background
engine.host.activeWhenUnfocused = true; // keep running behind another window
```

`activeWhenUnfocused` defaults to `false`, so clicking away from the window
counts as going to the background. It is the only setting, which is what keeps
scenes and audio from disagreeing about what "in the background" means. One
consequence: a game in a page frame starts unfocused until the player clicks
it, so with `scenes.autoPause` on it holds there, audio included; set
`engine.host.activeWhenUnfocused = true` to keep it running.

Two events carry the state to game code. `host:active` fires when
`engine.host.active` flips; `host:lifecycle` fires on every change of the three
states, for a game that wants the detail. When a handler changes the host
state, for example by setting `engine.host.activeWhenUnfocused`, every handler
receives the current change first and the new one after it.

```typescript
import { Component } from "@yagejs/core";

declare function writeCheckpoint(): void;

class CheckpointOnBackground extends Component {
  onAdd(): void {
    this.listenBus("host:active", ({ active }) => {
      if (!active) writeCheckpoint();
    });
  }
}
```

In a browser the page supplies two of the three: `visibility` follows the
page's own visibility, `focus` follows the window's `focus` and `blur` events,
and `activity` stays `"unknown"` because a page cannot see it. A host adapter
replaces any of them.

### Writing a host adapter

The Electron adapter ships as `@yagejs/host-electron`, together with the
shell it talks to; see [Desktop with Electron](/guides/electron/). The
Capacitor adapter ships as `@yagejs/host-capacitor`; see
[Mobile with Capacitor](/guides/capacitor/). Write your own for another
application.

A host adapter is a plugin named `"host"`. It reads the shell's own state,
attaches it in `install`, and releases it in `onDestroy`. One engine takes one
adapter: a second `attach` throws, and `engine.use` refuses a second plugin
named `"host"`.

```typescript
import { HostKey } from "@yagejs/core";
import type {
  EngineContext,
  HostInfoInput,
  HostLifecycleReport,
  Plugin,
} from "@yagejs/core";

declare function readShellInfo(): Promise<HostInfoInput>;
declare function readShellState(): Promise<HostLifecycleReport>;
declare function onShellStateChange(
  listener: (state: HostLifecycleReport) => void,
): () => void;

class ShellHostPlugin implements Plugin {
  readonly name = "host";
  readonly version = "1.0.0";

  private detach: (() => void) | undefined;
  private released = false;

  async install(context: EngineContext): Promise<void> {
    const info = await readShellInfo();
    // destroy() can run while install awaits, so check after every await.
    if (this.released) return;
    const lifecycle = await readShellState();
    if (this.released) return;
    this.detach = context.resolve(HostKey).attach({
      info,
      lifecycle,
      watchLifecycle: (report) => onShellStateChange(report),
    });
  }

  onDestroy(): void {
    this.released = true;
    this.detach?.();
    this.detach = undefined;
  }
}
```

Every `install` finishes before the loop starts and before any `onStart` runs,
so the host's state is in place before the first scene. `attach` validates
every field it is given and throws when one is wrong, then copies and freezes
them:
changing the provider's object afterwards does not change `engine.host`. The
function `attach` returns stops the reports and hands every state back to the
page, and a plugin that reads `engine.host.info` without depending on the
adapter reads it in `onStart`.

`lifecycle` is the shell's state at attach, read once like `info`.
`watchLifecycle` is called once; the adapter reports whichever of the three
states changed and returns the function that stops the reports. For each state
the adapter reports, its value is the answer and the page's is ignored, so a
shell whose window focus the page reads wrongly can correct it.

Fullscreen and screen orientation reach the engine the same way, through
`@yagejs/renderer`. An adapter registers a `HostDisplay` under
`HostDisplayKey` in its `install`, with a `fullscreen` part, an `orientation`
part, or both, and `RendererPlugin` reports whichever parts it finds there and
takes the rest from the page. A shell whose window fullscreen the page cannot
read supplies fullscreen and leaves orientation alone:

```typescript
import { HostDisplayKey } from "@yagejs/renderer";
import type { EngineContext, Plugin } from "@yagejs/core";
import type { HostFullscreen } from "@yagejs/renderer";

declare const shellFullscreen: HostFullscreen; // the shell's own window state
declare function onShellFullscreenChange(listener: () => void): () => void;

class ShellHostPlugin implements Plugin {
  readonly name = "host";
  readonly version = "1.0.0";

  install(context: EngineContext): void {
    context.register(HostDisplayKey, {
      fullscreen: shellFullscreen,
      watch: (changed) => onShellFullscreenChange(changed),
    });
  }
}
```

`HostDisplayKey` is also exported from `@yagejs/renderer/api`, the entry
without Pixi, so an adapter package can import it without loading the
renderer's drawing code. The renderer resolves the key when the engine starts,
after every `install` has run.

### Support

One set of words describes what a host can do, and every operation that needs
them uses these: `HostSupport` is `"supported"`, `"unsupported"` or
`"unknown"`, and answers whether the host has the operation at all.

Reading it never shows a permission prompt. `"unknown"` is what a host reports
when it cannot observe the state, so a game is never given a guess. Whether an
operation works at this moment — the hardware is present, a stream starts —
comes back from the operation itself, not from a stored status. The package
that owns an operation reports its support beside it.
