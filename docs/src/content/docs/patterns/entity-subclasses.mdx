Entity subclasses are the recommended way to define reusable entity types in
YAGE. They give you a typed `setup()` method for initialization and work
naturally with TypeScript's type system.

## Basic Subclass

```typescript yage-group="page" yage-context="scene"
import { Component, Entity, ProcessComponent, Transform, Vec2 } from "@yagejs/core";
import { SpriteComponent, type TextureRef } from "@yagejs/renderer";

class HealthComponent extends Component {
  current: number;

  constructor(options: { max: number }) {
    super();
    this.current = options.max;
  }
}

interface PlayerParams {
  position: Vec2;
  texture: TextureRef;
}

class Player extends Entity {
  setup(params: PlayerParams) {
    this.add(new Transform({ position: params.position }));
    this.add(new SpriteComponent({ texture: params.texture }));
    this.add(new ProcessComponent());
    this.add(new HealthComponent({ max: 100 }));
  }
}
```

Spawn it from a scene:

```typescript yage-group="page" yage-context="scene"
import { texture } from "@yagejs/renderer";

const heroTexture = texture("assets/hero.png");

const player = scene.spawn(Player, {
  position: new Vec2(100, 200),
  texture: heroTexture,
});
```

`scene.spawn()` infers the params type from the class, so you get full
autocomplete and type checking. If you omit a required `setup()` field, the
error names the field that's actually missing (`Property 'spawnPoint' is
missing`) rather than blaming an unrelated property.

## Why setup() Instead of constructor

The `constructor` runs before the entity is wired into the scene's ECS world.
At that point the entity has no scene reference, no access to engine services,
and components cannot query siblings.

`setup()` is called **after** the entity is registered with the scene, so you
can safely:

- Resolve services (`this.scene.use(...)`)
- Query the scene for other entities
- Emit events that other entities can receive
- Add components that depend on the scene context

If `setup()` throws, the error reaches the `scene.spawn()` caller unchanged and
the entity stays in the scene, holding the components it managed to add and any
children it already spawned. It is left there to be inspected. Use
`scene.spawnBatch` when a half-built entity would be worse than none; a batch
discards everything it reserved.

```typescript
import { Entity, Transform, type Vec2 } from "@yagejs/core";
import { ColliderComponent, RigidBodyComponent } from "@yagejs/physics";

interface EnemyParams {
  position: Vec2;
}

class Enemy extends Entity {
  setup(params: EnemyParams) {
    // Safe — the entity is attached to the scene, so scene-dependent
    // components (physics body, collider) can be added here.
    this.add(new Transform({ position: params.position }));
    this.add(new RigidBodyComponent({ type: "dynamic" }));
    this.add(new ColliderComponent({ shape: { type: "circle", radius: 16 } }));
  }
}
```

One thing `setup()` cannot do is reach its parent. `parent.spawnChild(name,
Class, params)` builds the child first and links it afterwards, so
`this.parent` is `null` for the whole of `setup()`, including the `onAdd()` of
every component that setup adds. The link exists as soon as `spawnChild`
returns.

Pass the parent in as a setup param when the child needs it. The param also
types it as the concrete parent class, which `this.parent` (typed
`Entity | null`) does not:

```typescript
import { Entity, Transform, Vec2 } from "@yagejs/core";

class Turret extends Entity {
  setup() {
    this.add(new Transform());
    this.spawnChild("barrel", Barrel, { owner: this });
  }
}

class Barrel extends Entity {
  private owner!: Turret;

  setup({ owner }: { owner: Turret }) {
    this.owner = owner; // usable immediately
    this.add(new Transform({ position: new Vec2(0, -8) }));
  }
}
```

When `setup()` has to read `this.parent` itself, build the pair in a
[spawn batch](/concepts/entities-and-components/#spawning-a-group-at-once):
`batch.addChild` links two reserved entities before `batch.setup` runs either
one.

An entity subclass exposes only `this.scene` — there is no `use()`,
`service()`, or `context` on the entity itself. To reach a service from
`setup()` or any method, go through the scene:

```typescript
import { Entity, RandomKey } from "@yagejs/core";
import { AudioManagerKey } from "@yagejs/audio";

class Crate extends Entity {
  setup() {
    const rng = this.scene.use(RandomKey);                        // scene scope, then engine; throws if missing
    const audio = this.scene.context.tryResolve(AudioManagerKey); // undefined if missing
  }
}
```

`this.scene.use(key)` checks scene scope first and engine scope second, so
per-scene infrastructure (the physics world, the render tree, the scene RNG)
and engine-wide services both resolve through the same call. `Component.use`
caches its result and `Scene.use` does not, so a lookup that runs every frame
belongs in a component.

## Traits

Traits define capabilities that cut across the class hierarchy. They are a
lightweight alternative to interfaces that work at runtime — you can check
whether an entity has a trait without knowing its concrete class.

### Defining a Trait

```typescript yage-group="page" yage-context="scene"
import { defineTrait } from "@yagejs/core";

const Interactable = defineTrait<{ interact(): void }>("Interactable");
const Damageable = defineTrait<{ takeDamage(amount: number): void }>("Damageable");
```

The type argument lists the members an entity with the trait must have.

### Applying Traits

Use the `@trait()` decorator on entity subclasses:

```typescript yage-group="page" yage-context="scene"
import { trait } from "@yagejs/core";

const chestTexture = texture("assets/chest.png");
const openChestTexture = texture("assets/chest-open.png");

interface ChestParams { position: Vec2 }
interface NPCParams { position: Vec2 }

declare function spawnLoot(position: Vec2): void;  // game code
declare function openDialogue(npc: NPC): void;     // game code

@trait(Interactable)
class Chest extends Entity {
  setup(params: ChestParams) {
    this.add(new Transform({ position: params.position }));
    this.add(new SpriteComponent({ texture: chestTexture }));
  }

  interact() {
    this.get(SpriteComponent).setTexture(openChestTexture);
    spawnLoot(this.get(Transform).position);
  }
}

@trait(Interactable)
@trait(Damageable)
class NPC extends Entity {
  setup(params: NPCParams) {
    this.add(new Transform({ position: params.position }));
    this.add(new HealthComponent({ max: 50 }));
  }

  interact() {
    openDialogue(this);
  }

  takeDamage(amount: number) {
    this.get(HealthComponent).current -= amount;
  }
}
```

### Querying by Trait

Use `entity.hasTrait()` as a type guard to discover capabilities at runtime:

```typescript yage-group="page" yage-context="scene"
import { PhysicsWorldKey } from "@yagejs/physics";

const playerPos = player.get(Transform).position;
const interactRadius = 48;

// Find all interactable entities near the player (any entity with a collider)
const nearby = scene.use(PhysicsWorldKey).queryRadius(playerPos, interactRadius);

for (const entity of nearby) {
  if (entity.hasTrait(Interactable)) {
    entity.interact(); // TypeScript knows this method exists
  }
}
```

Use `entityClassHasTrait()` when code must validate a class before it creates
an instance. The check includes traits inherited from parent classes:

```typescript yage-group="page" yage-context="scene"
import { entityClassHasTrait } from "@yagejs/core";

if (!entityClassHasTrait(Chest, Interactable)) {
  throw new Error("Chest must implement Interactable");
}
```

This pattern is useful for interaction systems — a single "press E to interact"
prompt can work with chests, NPCs, doors, and any future entity that gains the
`Interactable` trait.

## Blueprints (Deprecated Alternative)

Blueprints (`defineBlueprint()`) are the older way to define entity factories.
They still work and you may encounter them in existing code, but entity
subclasses are preferred for new code because they offer better type safety
and a more natural class-based API.

```typescript yage-context="scene"
// Legacy approach — still functional, but prefer entity subclasses
import { defineBlueprint, Transform, Vec2 } from "@yagejs/core";
import { SpriteComponent, texture } from "@yagejs/renderer";

const coinTexture = texture("assets/coin.png");

interface CoinParams {
  position: Vec2;
}

const CoinBlueprint = defineBlueprint("Coin", (entity, params: CoinParams) => {
  entity.add(new Transform({ position: params.position }));
  entity.add(new SpriteComponent({ texture: coinTexture }));
});

const position = new Vec2(64, 32);
const coin = scene.spawn(CoinBlueprint, { position });
```

If you're starting a new project, use entity subclasses. If you're maintaining
code that already uses blueprints, there is no urgency to migrate — both
patterns coexist without conflict.
