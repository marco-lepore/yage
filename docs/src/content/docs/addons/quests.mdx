`@yagejs-addons/quests` is a headless quest log: a `QuestLog` model that owns
quest phases (active/completed/failed), per-objective progress, prerequisite
chains, and auto-complete rollup — the logic every RPG rewrites. It is pure
`@yagejs/core`: no renderer, no dialogue or inventory dependency, no
presenters. A journal or tracker HUD reads the model directly; the addon just
tracks state and emits consequences.

## Install

```bash
npm install @yagejs-addons/quests
npm install @yagejs/core
```

`@yagejs/core` is the only peer. There is no `./presenters` subpath — the
whole package is headless.

## Define quests, start one

Quest ids come from the map keys; each quest's objective ids come from its own
nested `objectives` map — so `log.advance("gatherHerbs", "herb")` type-checks
and `log.advance("gatherHerbs", "wolf")` doesn't, with no type argument written
anywhere.

```ts yage-group="herbs"
import { defineQuests, QuestLog } from "@yagejs-addons/quests";

const quests = defineQuests({
  gatherHerbs: {
    title: "Gather Herbs",
    summary: "The healer needs red herbs.",
    objectives: {
      herb: { title: "Collect red herbs", count: 5 }, // target 5
      turnIn: { title: "Return to the healer" }, // count omitted -> target 1
    },
  },
  thinThePack: {
    title: "Thin the Pack",
    requires: ["gatherHerbs"], // locked until gatherHerbs is completed
    objectives: { wolf: { title: "Slay wolves", count: 3 } },
  },
});

const log = new QuestLog(quests);
log.start("gatherHerbs"); // { ok: true } — prereqs met (none)
```

A quest log is progression that the game saves and keeps from scene to scene,
so it sits at module level next to the game's save root (see [Save](#save)).
Components read and advance it from there.

## Bind objectives to other addons — no addon dependency

Quests declares no dependency on dialogue, inventory, or any other addon.
Instead, the game subscribes to whatever events it likes and calls
`advance`/`complete` — a one-line adapter per binding, with **no active-state
guard needed**: the log silently ignores progress calls on a quest that isn't
currently active, so firing unconditionally on every pickup/kill is correct.

```ts yage-group="herbs"
import { Component, defineEvent } from "@yagejs/core";
import { DialogueController, type DialogueScript } from "@yagejs-addons/dialogue";
import { InventoryItemAddedEvent } from "@yagejs-addons/inventory";

// The game's own entity event, emitted by a wolf when it dies.
const WolfDiedEvent = defineEvent("game:wolf-died");

/** Turns game events into quest progress. Add it to the player. */
class QuestProgress extends Component {
  onAdd(): void {
    // Inventory pickup on the player -> advance the collect objective.
    this.listen(this.entity, InventoryItemAddedEvent, (e) => {
      if (e.itemId === "redHerb") log.advance("gatherHerbs", "herb", e.quantity);
    });

    // The game's own entity event, bubbling up from any wolf -> advance wolf kills.
    this.listenScene(WolfDiedEvent, () => log.advance("thinThePack", "wolf"));
  }
}

/** On the healer, next to its DialogueController. */
class HealerTalk extends Component {
  private readonly dialogue = this.sibling(DialogueController);

  talk(healerScript: DialogueScript): void {
    // Dialogue command -> complete the turn-in objective (the healer's script
    // fires a `turnIn` command, such as `do turnIn`, handled by a command
    // handler injected at play() time).
    this.dialogue.play(healerScript, {
      commands: { turnIn: () => log.complete("gatherHerbs", "turnIn") },
    });
  }
}
```

<Aside type="tip">
This is the whole binding mechanism — one handler per objective, driven by
your game's own events. Quests stays decoupled from inventory and dialogue: you
translate their events into `advance()` calls yourself.
</Aside>

## React to consequences

React from a component. `log.on(...)` returns an unsubscribe function; pass it
to `addCleanup` so the subscription ends when the component is removed:

```ts yage-group="herbs"
import { TextComponent } from "@yagejs/renderer";

/** On the HUD's quest label: progress, completion, and the next quest. */
class QuestTracker extends Component {
  private readonly text = this.sibling(TextComponent);

  onAdd(): void {
    this.addCleanup(
      log.on("objectiveProgressChanged", ({ progress, count }) => {
        this.text.setText(`${progress}/${count}`); // "3/5"
      }),
    );
    this.addCleanup(
      log.on("questCompleted", ({ questId }) => {
        // Event payloads carry string ids; tryGet looks one up without a cast.
        this.text.setText(`Quest complete: ${quests.tryGet(questId)?.title ?? questId}`);
        if (questId === "gatherHerbs") log.start("thinThePack"); // chain, one line
      }),
    );
  }
}
```

Model events: `questStarted`, `objectiveProgressChanged { progress, count, done }`,
`objectiveCompleted`, `questCompleted`, `questFailed`, and a coarse `changed`
after every mutating call.

## Reading state (what a journal/tracker needs)

```ts yage-group="herbs"
log.status("thinThePack"); // "locked" | "available" | "active" | "completed" | "failed"
log.available(); // QuestId[] — startable now (prereqs met, not started)
log.active(); // QuestId[]
log.progress("gatherHerbs", "herb"); // 3
log.objectiveDone("gatherHerbs", "herb"); // false
log.canComplete("gatherHerbs"); // false
log.get("gatherHerbs"); // full QuestState { status, objectives: {...counts} }
```

`status()` returns the stored phase (active/completed/failed) for a started
quest. A never-started quest is `available` once every quest in its `requires`
is `completed`, and `locked` until then.

## Prerequisites

`requires` is a flat list of quest ids that must be `completed` before a quest
unlocks — no nested graph object. Forward references (naming a later-declared
quest) are fine; naming a quest absent from the whole `defineQuests` call throws
at definition time. A prerequisite **cycle** leaves its
quests `locked` forever (no crash) — each waits on another that never completes.
`fail` is terminal, so a failed quest never reaches `completed` again — any
quest that `requires` it stays `locked` permanently.

## Auto-complete rollup

A quest completes automatically the moment every non-`optional` objective
reaches its target — no explicit "finish quest" call needed for the common
case. `optional` objectives never gate completion:

```ts
import { defineQuests } from "@yagejs-addons/quests";

defineQuests({
  q: {
    title: "Explore the Ruins",
    objectives: {
      artifact: { title: "Recover the artifact" }, // required
      secretDoor: { title: "Find the secret door", optional: true },
    },
  },
});
// Completing "artifact" alone completes the quest; "secretDoor" can stay
// untouched.
```

Set `autoComplete: false` when the game must explicitly turn in a quest.
`completeQuest(quest)` then completes the quest only while it is active and
every required objective is currently done. `forceCompleteQuest(quest)` marks
every objective done and completes the quest regardless of prerequisites or
progress; use it for scripts, cheats, and tests.

## Current-state objectives

Use `setProgress()` when an objective represents current state rather than a
cumulative total. The quest must use `autoComplete: false` so reaching the
target does not make completion permanent before the player turns it in.

```ts yage-group="wood"
import { defineQuests, QuestLog } from "@yagejs-addons/quests";
import { defineItems, Inventory } from "@yagejs-addons/inventory";

const quests = defineQuests({
  bringWood: {
    title: "Bring Robin 10 wood",
    autoComplete: false,
    objectives: { wood: { title: "Have 10 wood", count: 10 } },
  },
});
const log = new QuestLog(quests);
const inventory = new Inventory({ catalog: defineItems({ wood: { name: "Wood" } }) });

const syncWood = () =>
  log.setProgress("bringWood", "wood", inventory.count("wood"));

inventory.on("itemAdded", syncWood);
inventory.on("itemRemoved", syncWood);
log.start("bringWood");
syncWood(); // Include wood already held when the quest starts.
```

If the player reaches 10 wood and then drops to 9, the objective becomes
incomplete again. The NPC can finish the quest only while the requirement is
satisfied:

```ts yage-group="wood"
if (log.canComplete("bringWood")) {
  log.completeQuest("bringWood");
}
```

Use `advance()` instead for an “obtain 10 wood” objective whose progress must
only increase.

## Optional engine-bus mirror

For a HUD or achievements system that shouldn't hold a `log` reference
directly, mount a `QuestController` on any persistent entity — it re-emits the
model's six events onto the engine bus (entity → scene):

```ts yage-group="herbs"
import type { Entity } from "@yagejs/core";
import { QuestController, QuestCompletedEvent } from "@yagejs-addons/quests";

declare const player: Entity; // the game's player entity

player.add(new QuestController({ log }));

/** Any component in the scene hears the mirrored events. */
class Achievements extends Component {
  onAdd(): void {
    this.listenScene(QuestCompletedEvent, ({ questId }) => this.check(questId));
  }

  private check(questId: string): void {
    // unlock whatever this quest earns
  }
}
```

The controller is entirely optional — `log.on(...)` reaches the same
consequences with no component at all.

Disabling `QuestController`, or deactivating its entity, stops this event
mirror. The standalone `QuestLog` remains live. Model events that occur while
the controller is dormant are not replayed when it enables.

## Save

`snapshot()` / `restore()` round-trip the whole log as plain JSON. Include the
quest data in the game's explicit save root:

```ts yage-group="herbs"
import type { Serializable } from "@yagejs/core";
import { createSave, localStorageAdapter } from "@yagejs/save";
import type { QuestSnapshot } from "@yagejs-addons/quests";

const save = createSave({ adapter: localStorageAdapter() });

const gameState: Serializable<{ quests: QuestSnapshot }> = {
  serialize: () => ({ quests: log.snapshot() }),
  hydrate: ({ quests }) => log.restore(quests),
};

await save.persist("game", gameState);
await save.restore("game", gameState);
```

`restore` drops quest ids the current catalog no longer declares and objective
ids no longer declared within a restored quest, clamping surviving counts to
the current target. A quest never started stays absent from the snapshot; its
status re-derives from `requires` on restore, same as before any snapshot
existed.

The full restored log is available before any listener runs. An active quest
that now meets every target auto-completes, for example after a catalog target
was reduced. Its `questCompleted` event precedes its `changed` event, so a
completion listener can start a dependent quest immediately. Restore does not
replay objective-completion events. Manual-completion quests and saved completed
or failed quests keep their status.
