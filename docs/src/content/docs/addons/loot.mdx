---
title: Loot Tables
description: Reproducible chest and enemy rewards with weighted pools, nested tables, conditions, and selection explanations
---

Loot tables turn a reward definition into typed item quantities. They handle
weighted choices, nested tables and draws without replacement. Your game chooses
what an item means and whether a rolled reward enters an inventory, appears in
the world or grants another benefit.

## Install and roll

```bash
npm install @yagejs-addons/loot @yagejs/core
```

```ts
import { createRandomService } from "@yagejs/core";
import { LootTables } from "@yagejs-addons/loot";

const loot = new LootTables({
  chest: { pools: [{ id: "reward", entries: [
    { id: "coins", kind: "item", item: "coin", quantity: { min: 2, max: 5 }, weight: 3 },
    { id: "ruby", kind: "item", item: "ruby" },
  ] }] },
});
const result = loot.roll("chest", { random: createRandomService(42) });
console.log(result.rewards); // Item, quantity and selection source for each reward.
console.log(result.trace); // Candidates, probabilities, exclusions and selections.
```

Every pool selects one entry per roll. An omitted weight is 1, so this pool
chooses coins three times as often as a ruby. Quantities default to 1. A quantity
range includes both endpoints. Every roll requires an explicit random source.

Try the [chest example](/examples/loot-addon.html). Open a chest, bank the backpack
contents, and change the player level. The canvas shows why the ruby was excluded
and which rewards the two-slot backpack could not accept.

## Compose guaranteed and optional rewards

Use separate pools when a chest should produce several independent rewards.
An unconditional single-entry pool guarantees its item when its weight, roll count
and quantity are positive. An `empty` entry makes receiving nothing an explicit
weighted outcome.

```ts
import { createRandomService } from "@yagejs/core";
import { LootTables } from "@yagejs-addons/loot";

type Item = "coin" | "herb" | "potion";
const loot = new LootTables<Item, void, "chest" | "supplies">({
  chest: { pools: [
    { id: "coins", entries: [{ id: "coins", kind: "item", item: "coin", quantity: 5 }] },
    { id: "bonus", entries: [
      { id: "bundle", kind: "table", table: "supplies", weight: 2 },
      { id: "nothing", kind: "empty" },
    ] },
  ] },
  supplies: { pools: [{ id: "supplies", rolls: 2, unique: true, entries: [
    { id: "herbs", kind: "item", item: "herb", quantity: { min: 1, max: 3 } },
    { id: "potion", kind: "item", item: "potion" },
  ] }] },
});
const result = loot.roll("chest", { random: createRandomService(42) });
console.log(result.rewards);
```

Pools run in definition order. A selected table expands immediately. Each nested
table starts a new invocation; the trace links it to the parent selection.

`unique: true` removes a selected **entry id** for that pool invocation. The same
item can appear through different entries or other pools. Empty entries and
nested-table entries also count as selections. Uniqueness resets for the next
invocation and the next call; it does not mean “once per player.” When the pool
runs out of eligible entries, its remaining draws stop with `no-eligible` in the
trace.

`rolls` accepts a fixed count or an inclusive range, and defaults to 1. Zero rolls
skip the pool. Zero item quantity consumes a draw but yields no reward. An empty
pool or a pool whose weights are all zero returns no rewards and explains the
empty outcome. Neither case is an error.

## Conditions and game-specific balance

Pass the values a drop rule needs as typed context. A condition returns `true`
when eligible, `false` for a general refusal, or a nonempty string explaining the
refusal. Weight callbacks can read level, luck or values from your stats model.

```ts
import { createRandomService } from "@yagejs/core";
import { Stats } from "@yagejs-addons/stats";
import { LootTables } from "@yagejs-addons/loot";

const stats = new Stats({ level: { base: 3 }, luck: { base: 4 } });
const loot = new LootTables<"ruby", { level: number; luck: number }>({
  chest: { pools: [{ id: "treasure", entries: [
    { id: "ruby", kind: "item", item: "ruby",
      when: ({ level }) => level >= 3 || "requires-level-3",
      weight: ({ luck }) => luck },
    { id: "nothing", kind: "empty", weight: 3 },
  ] }] },
});
const result = loot.roll("chest", {
  random: createRandomService(42), context: stats.values(),
});
console.log(result.trace);
```

A pool can have its own `when` condition. Pool conditions run before sampling the
roll count. Entry conditions and weights run once per nonzero pool invocation,
in entry order. Refused entries do not evaluate their weight callback. A nested
invocation evaluates its own policies again. Callbacks must be synchronous and
pure; do not mutate game state or consume random values inside them.

Weights must be finite and nonnegative. Zero disables an entry. Probabilities are
relative to the eligible entries on each draw, so removing an entry changes the
remaining probabilities. Very small probabilities are limited by floating-point
precision and the random generator's resolution.

The item type can be an id, a plain reward object or another game-owned value.
The addon keeps the original value by reference. It does not clone or freeze your
item objects. The definition containers are copied and frozen when constructed;
create another model when your definitions change.

## Use a scene component

```ts yage-context="entity"
import { LootComponent, LootRolledEvent, LootTables } from "@yagejs-addons/loot";

const tables = new LootTables({ chest: { pools: [{ id: "coins", entries: [
  { id: "coins", kind: "item", item: "coin", quantity: 5 },
] }] } });
const loot = entity.add(new LootComponent(tables));
entity.on(LootRolledEvent, ({ table, rewardCount }) => console.log(table, rewardCount));
const result = loot.roll("chest");
console.log(result.rewards);
```

`LootComponent` supplies the scene's `RandomKey` and the engine's error boundary.
Its `roll(table, context?)` method returns typed rewards. It also stores `lastRoll`
and emits `LootRolledEvent` after completing the roll. The event's `rewardCount`
is the number of reward stacks, not the sum of item quantities. `lastRoll` is
initially null and remains the previous completed result if a later roll fails.

The component must be attached and enabled on an active, live scene entity. Its
`model` stays public, so headless calls are available separately. You can provide
a custom implementation of `LootModel` or pass a dedicated random generator as
the constructor's second argument. The standard stateless model can be shared
by several components. There is no update loop or plugin to install.

## Inspect and reproduce a roll

`result.trace` records each pool and selection, its candidates, effective weights,
probabilities and exclusion reasons. Reward `source` records identify the table,
pool, table invocation, draw and entry. Nested traces include the parent source.
Rewards remain separate even when they contain the same item.

With `debug: true` and an installed `InspectorPlugin` or `DebugPlugin`, read
`inspector.getComponentData(entityName, "LootComponent")`. Its `diagnostics` field
contains the trace, random draw count, reward quantities and source ids. It leaves
out item values, so cyclic objects or custom serialization cannot hide the
explanation. Read `loot.lastRoll` directly when you need the original items. Both
readings are initially null. Roll events appear in the Inspector event log.

Use the same seed, definitions, context and call order to reproduce a sequence.
A scene generator shares its sequence with other game systems. For an independent
stream, retain a dedicated `createRandomService(seed)` and pass it to each roll.
Creating a new generator with the same seed for every call repeats the first roll.

Every weighted selection consumes one random value, including a single-candidate
pool. Nonconstant count ranges consume another value; fixed counts consume none.
`randomDraws` counts these calls. An empty eligible pool consumes no selection
value. A custom source only needs `float(): number`, returning a finite value in
`[0, 1)`. Changing definitions or callback behavior can change consumption order.

## Validation and failures

Construction rejects malformed definitions, duplicate ids, unknown nested tables
and cycles, even in unused or disabled entries. Counts and range endpoints must
be nonnegative safe integers; the inclusive range size must also be safe.
Nesting is limited to 64 tables.

The optional constructor setting `maxWork` defaults to 100000. It bounds candidate
visits and nested rolls using maximum roll counts and the most expensive nested
branch. The bound is conservative: conditions and uniqueness do not reduce it.
A roll that exceeds the bound throws before callbacks or randomness. Reduce the
definition's work or explicitly raise the limit to a positive safe integer below
`Number.MAX_SAFE_INTEGER`.

A throwing callback or invalid callback result stops the roll. Conditions, weight
callbacks and random calls are recorded through `ErrorBoundary.wrapCallback` with
the definition path. Component calls also record the entity and scene names.
Headless callers can supply those names through `errorContext: { entity?, scene? }`
in roll options. Read the component's engine errors through
`inspector.getErrors().callbackErrors`. Headless models expose `errorBoundary` and
accept a boundary in constructor options or per-roll options.

Already consumed random values are not rolled back after a failure. The result
is published before the entity event; a throwing listener stops later listeners
but leaves the completed result available.

## Grant rewards and save progress

When the item values are inventory ids, grant them through the existing inventory
API. A partial add is a normal outcome:

```ts
import { Inventory, defineItems } from "@yagejs-addons/inventory";
import type { LootReward } from "@yagejs-addons/loot";

const bag = new Inventory({ catalog: defineItems({ coin: { name: "Coin", maxStack: 10 } }), capacity: 2 });
function collect(reward: LootReward<"coin">) {
  const result = bag.add(reward.item, reward.quantity);
  // Keep this quantity available for another pickup attempt.
  return { item: reward.item, quantity: result.rejected, reason: result.reason };
}
console.log(collect);
```

Use inventory's `transfer` to move accepted items to another inventory. Your game
can instead spawn pickups or grant a different reward type. Rolling alone does
not claim a chest or guarantee inventory acceptance.

The addon owns no durable progress, so it has no snapshot or restore methods.
Store opened-chest flags, unclaimed rewards, pity counters or permanent unique
rewards in your game's controlled save root. Save granted inventory through its
own snapshot. For reproducible independent chests, save a per-chest seed and its
claimed state: a generator's seed alone does not capture its current position.
Item values must be serializable if you store rolled rewards directly.
